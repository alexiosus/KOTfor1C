# ИИ-оператор тестирования

KOT предоставляет внешнему ИИ-агенту MCP-инструменты для исходников, выполнения Vanessa, исследования форм и данных, исправлений и отчётов. Модель и её диалог работают в выбранном пользователем клиенте. Прямая генерация через API удалена; [описания сценариев можно заполнять через агента](ai-description.md), прежние отчёты остаются доступны.

## Подключить агента

### Быстрое подключение для нового тестировщика

1. Установите KOT из актуального VSIX, Node.js 20 или новее и настройте выбранный ИИ-клиент. Откройте тестовый проект в доверенном окне VS Code. Для запуска тестов нужен обычный рабочий профиль KOT с платформой 1С, Vanessa и компилятором СППР, если он используется в проекте.
2. В настройках KOT нажмите **Подключить ИИ** либо выполните **KOT: Подключить ИИ-агента** через `Ctrl+Shift+P`.
3. Выберите **Codex**, **Claude Code** или **Другой MCP-клиент**, затем разрешения: **Запускать и исправлять тесты**, **Только анализ** или **Запускать и исправлять тесты и конфигурацию**. Первый вариант требует согласования продуктовых правок и существующих assertions.
4. Мастер запустит KOT и проверит Node.js и настоящий маршрут MCP. Для Codex и Claude Code он добавит сервер в настройки проекта и установит скилл. Настройки остальных серверов сохраняются; перед изменением существующих файлов создаются резервные копии в `<runtime>/agent/setup-backups`. При конфликте с чужим сервером `kot` или изменённым скиллом мастер остановится. Для другого MCP-клиента откроется памятка с готовой конфигурацией, первым запросом и проверкой доступных инструментов.
5. Завершите подключение выбранного клиента **в этом проекте** и начните новую сессию. Подтвердите доверие к проекту и подключению, если клиент спросит. Кнопка **Скопировать первый запрос** готовит запрос проверки доступных тестов. Затем поставьте свою задачу обычным текстом.

Для Codex используются `.codex/config.toml` и `.agents/skills/kot-testing/SKILL.md`; для Claude Code — `.mcp.json` и `.claude/skills/kot-testing/SKILL.md`. Подключение действует для выбранного проекта, глобальные профили не меняются. Codex читает проектные настройки только в доверенных проектах; Claude Code может запросить подтверждение проектного MCP. Это штатные правила клиентов: [OpenAI Docs — MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli), [Claude Code — MCP](https://code.claude.com/docs/en/mcp).

KOT включит запуск сервера при следующих открытиях проекта. Мост хранится в runtime и обновляется вместе с сервером, поэтому путь к версии расширения не попадает в настройки клиента. После обновления KOT снова запустите мастер для обновления скилла. Подключение к ИИ и подготовка 1С — отдельные проверки: наличие MCP не подтверждает готовность тестовой базы. Режим **Только анализ** доступен без запущенной 1С. Регистрацию аккаунта, ограничения клиента и установку отсутствующей платформы 1С мастер не обходит.

Слева в строке состояния, рядом с Vanessa, показан **KOT Agent**: запущен, остановлен, запуск/остановка или ошибка. Нажатие запускает либо останавливает MCP-сервер в текущем окне; настройка автозапуска сохраняется. При ошибке нажатие повторяет запуск. Во время перехода виден спиннер, нажатие временно отключено. Подсказка запущенного сервера содержит локальный адрес без токена доступа. Индикатор отражает состояние сервера KOT; подключение ИИ-клиента проверяется отдельно вызовом `kot_project`.

Примеры первого рабочего запроса:

> Используй скилл kot-testing. Разбери архив CI `C:\CI\Tests_01_failed.zip`. Восстанови отдельную копию базы, проверь ветку и контекст, продолжи оставшуюся группу Tests_01 и дай отчёт. Изменения бизнес-ожиданий согласуй со мной.

> Используй скилл kot-testing. На свежей копии `C:\Tests\before-feature.dt` запусти группу Purchases. Исследуй падения, предложи или примени разрешённые исправления и подтверди их полным прогоном из начального состояния.

### Ручное подключение и другие MCP-клиенты

В мастере выберите **Другой MCP-клиент**. После проверки соединения KOT откроет `<runtime>/agent/connect-mcp-client.md`. Кнопка **Скопировать настройки MCP** копирует JSON с командой `node` и аргументами моста. Если оболочка использует другую структуру настроек, перенесите `command` и `args` из `mcpServers.kot` в её поля подключения stdio-сервера. Памятка сохраняется в runtime и доступна после закрытия уведомления.

Первый запрос этого режима использует `kot_project`, `kot_runtime` и `kot_workflow`; установка скилла и поддержка MCP-prompts не требуются. Клиент должен запускаться на том же компьютере и поддерживать MCP через stdio. Мастер проверяет локальный маршрут до KOT; подключение из конкретной оболочки завершается и проверяется в ней самой. Её файлы настроек остаются под управлением пользователя.

Для подключения без мастера:

1. Откройте доверенный проект в VS Code. Для выполнения подготовьте платформу 1С, Vanessa, тестовую базу и профиль сборки. Чтение исходников и подготовка тест-плана доступны без работающей 1С.
2. Выполните **KOT: Агент: запустить MCP-сервер и открыть настройки подключения**. Откроется `mcp.json` из `<runtime>/agent/`.
3. Передайте внешнему MCP-клиенту команду `node` и массив `args` из этого файла. JSON с `mcpServers` подходит клиентам, использующим такой формат; в другом клиенте настройте тот же stdio-сервер его штатным способом. Для моста требуется Node.js 20 или новее.
4. Проверьте, что агент видит инструменты `kot_project`, `kot_runtime`, `kot_run_start`, `kot_workflow`, `kot_actions`. Рабочие процессы `run_and_repair`, `investigate`, `resume`, `story`, `review`, `generate` доступны через `kot_workflow`; при поддержке MCP-prompts они также представлены инструкциями с префиксом `kot_`.

Локальный HTTP-сервер слушает `127.0.0.1`, проверяет авторизацию, Origin и доверие workspace. Stdio-мост читает реквизиты соединения из локального `connection.json`; ключ не требуется вставлять в диалог. При перезапуске сервера переподключите MCP-клиент. Команда остановки удаляет файл текущего подключения.

По умолчанию runtime находится в `.vscode/kot-runtime`. История хранится в `agent/operations`. Не включайте runtime с локальными артефактами и подключением в Git. Настройка `runtime.directory` может задавать другой каталог.

### Подключить скилл KOT

При запуске MCP-сервера KOT выгружает готовый скилл в `<runtime>/agent/skills/kot-testing/SKILL.md`. Скопируйте **весь каталог `kot-testing`** в каталог скиллов выбранного клиента:

| Клиент | Для текущего проекта | Для всех проектов пользователя |
| --- | --- | --- |
| Codex | `.agents/skills/` | `~/.agents/skills/` |
| Claude Code | `.claude/skills/` | `~/.claude/skills/` |

После копирования начните новую сессию агента в тестовом проекте. Пути установки указаны в [официальной документации OpenAI](https://developers.openai.com/api/reference/cli#agent-skill). Скилл поставляется с расширением; после обновления KOT обновите его копию. Расширение не меняет глобальные инструкции агента или `AGENTS.md`/`CLAUDE.md` автоматически.

Пример запроса: «Используй скилл `kot-testing`. Разбери этот архив CI, восстанови контекст на копии базы и продолжи всю группу Tests_01. Сохраняй основания исправлений и отчёт».

MCP необходим для действий, скилл задаёт порядок работы. Поддержка MCP-prompts зависит от клиента; инструмент `kot_workflow` отдаёт те же актуальные инструкции через обычный вызов инструмента. Длинное восстановление контекста подробно описано в workflow `resume`, поэтому правила не нужно каждый раз пересказывать в диалоге.

## Остальные операции KOT

Агент может пользоваться менеджером баз, сохранёнными клиентами, настройками и профилями, создавать и переименовывать сценарии, заполнять свойства и параметры, управлять группами, избранным, вложениями и библиотеками, отлаживать и записывать действия. Полный актуальный список он получает через `kot_actions`; [справочник API](../technical/agent-api.md) описывает области доступа.

Достаточно запроса в чате, например: «Переименуй запись этой базы в лаунчере в KOT-test-ib», «Создай основной сценарий по этим проверкам и заполни описание» или «Добавь этот MXL к сценарию». Вопросы штатных мастеров доступны агенту через API. Для неоднозначного выбора либо разрушительного действия требуется ваше решение о конкретной цели; агент не должен отвечать на такие подтверждения по догадке. Завершение команды не означает прохождение теста — результат проверяется чтением и, когда нужно, запуском.

После обновления расширения перезапустите сервер KOT и переподключите MCP-клиент, чтобы обновился список инструментов. Для обновления установленного скилла повторите мастер **Подключить ИИ**; неизменённая установленная версия обновится штатно, а ваши ручные правки будут сохранены как конфликт для разбора. Другому MCP-клиенту достаточно новых инструментов и `kot_workflow`.

Настройки подтверждений отдельных инструментов Codex (`mcp_servers.kot.tools`) сохраняются при повторном подключении и не мешают обновлению скилла. Если изменены команда или аргументы запуска KOT, мастер по-прежнему остановится для проверки.

Для базы в конкретном каталоге агент использует штатное действие `infobase.create`, а не `kot_environment`, которое выбирает изолированный каталог само. При передаче внешнего пути к DT или новому каталогу KOT покажет окно **Разрешить агенту KOT доступ к этому пути?** с точным путём. Подтвердите его в VS Code; агент продолжит операцию. Доступ действует до остановки сервера и не меняет `agent.allowedRoots`. Отказ сохраняет запрет, а приватные пути остаются закрыты. Заранее создавать каталог либо редактировать JSON для этого не требуется.

## Запустить и исправить тесты

Пример запроса внешнему агенту:

> Используй workflow kot_run_and_repair. Найди группу продаж, покажи выбранные тесты и запусти их по порядку на указанной тестовой базе. Ошибки тестов исправляй в пределах политики KOT, продуктовые ошибки подготовь для согласования. Сохраняй гипотезы, изменения и проверочные прогоны. В конце дай отчёт.

Агент получает реальные идентификаторы тестов из `kot_project`; имена и группы используются для выбора, не как неоднозначные идентификаторы. `kot_run_start` возвращает ID операции. `kot_operation` показывает статус, порции событий и ссылки на артефакты. Повторный запрос с тем же `requestKey` не запускает второй тест. Для нового эксперимента нужен новый ключ.

Также доступна команда **Агент: запустить тесты** с множественным выбором. Она запускает исполнитель. Для автоматического исследования и исправлений подключённый агент должен вести задачу по workflow; запуск команды сам по себе не создаёт отдельную модель или фоновый диалог.

СППР собирается существующим компилятором и активным профилем, включая выбор корневых исходников и контроль актуальности. Самостоятельная feature проверяется и выполняется без компилятора СППР. Запускаются сохранённые исходники. При ошибке фиксируются доступные диагностика, форма, журнал, версия исходников и карта упавшей строки. Остаток набора сохраняется в результате операции.

Перед выполнением KOT проверяет `КаталогПроекта` из JSON выбранного теста и подтверждает его значение в Vanessa, чтобы одноимённые макеты из другого проекта не попадали в сравнения. Для самостоятельной feature учитывается связанный JSON, при его отсутствии используется каталог feature. Для этой подготовки нужен API настроек Vanessa; отсутствие возможности подтверждения не считается успешной подготовкой. Автоматический сбор ошибки сначала сохраняет исходную форму; журнал регистрации клиента без проверенного VAExtension не запрашивается, поскольку такой запрос способен открыть дополнительное окно ошибки.

Тесты выполняются последовательно. Их подготовка данных, зависимости и сброс состояния остаются частью тестового проекта. Исполнитель не объявляет произвольные тесты независимыми и не сбрасывает общую базу между ними автоматически.

`agent.runTimeoutMinutes` задаёт длительность запроса выполнения Vanessa; по умолчанию 120 минут. После изменения переподключите менеджер. `agent.maxRepairAttempts` ограничивает число применённых исправлений, связанных с одним расследованием; по умолчанию три. Общие настройки доступны на странице KOT в разделе **Агент тестирования**.

При несовпадении дат или чисел агент сначала проверяет окружение. `kot_launch_settings` с `action: read` возвращает активный профиль сборки, его ревизию и параметры клиента с удалёнными секретами. Для изменения передайте `action: set`, текущую `expectedRevision`, `interfaceLanguage` и/или `locale`, а также `requestKey`. Например, `interfaceLanguage: en` и `locale: en` задают `/Len /VLen`. Меняются параметры профиля KOT; системные настройки Windows и ожидания теста не меняются. Обновление сохраняется в истории, отклоняется при смене профиля или занятом исполнителе. Затем закройте прежний клиент, пересоберите тест и проверьте его на свежей базе из начального DT. Правка файла начальных профилей на диске не заменяет обновление активного профиля, сохранённого в KOT.

## Выбрать базу и подготовить копию

Чтобы задать имя базы в лаунчере, попросите агента: «Создай базу из этого DT и назови `KOT-test-ib`». Для `kot_environment` используется `action: create`, `sourceKind: dt`, путь `source`, `name: KOT-test-ib` и новый `requestKey`. Это имя записи списка 1С; каталог базы создаётся в изолированном окружении KOT. Проверьте `result.launcher.registeredName`: если имя занято другой базой, возможен суффикс. Повторная регистрация сохраняет имя исходного запроса, но не переименовывает уже существующую запись. [Точная граница возможностей менеджера через MCP](../technical/agent-api.md#менеджер-баз-и-доступ-агента).

`kot_client` показывает сохранённые и живые профили, подключает выбранный `profileId` либо существующий живой профиль по `name`, явно закрывает/отключает именованный клиент. Пароли остаются локально; сохранённые профили используют KOT SecretStorage.

`kot_manager` перечисляет доступные локальные менеджеры Vanessa и связь с текущим workspace. Можно явно подключить выбранный endpoint либо запустить управляемый менеджер. При нескольких сеансах без однозначной связи API возвращает необходимость выбора; диалог VS Code не блокирует агента. Для изменения менеджера, подключения клиента, записи переменной и действий с формой передавайте отдельный `requestKey`.

`kot_environment` создаёт отдельную файловую базу:

- `sourceKind: dt` — из сохранённого DT;
- `sourceKind: cf` — новая база с загрузкой CF;
- `sourceKind: sources` — новая база из файловой выгрузки конфигурации;
- `sourceKind: empty` — пустая база платформы, без прикладной конфигурации.

После успешной подготовки KOT регистрирует базу в списке запуска 1С и обновляет раздел информационных баз. Имя содержит проект и короткий ID окружения. Результат регистрации находится в `result.launcher`: `added`, `alreadyExists`, `unsupported` или `failed`. Ошибка списка запуска не отменяет готовность самой базы и сохраняется в истории операции. Для повторной регистрации, в том числе базы из прежней версии KOT, вызовите `kot_environment` с `action: register`, её `environmentId` и новым `requestKey`; повторного восстановления DT не будет.

Источники должны находиться в workspace или в явно настроенных `agent.allowedRoots`. При создании из исходников/CF необходимые прикладные данные готовит сценарий либо отдельная процедура проекта. KOT не выводит правила заполнения произвольной конфигурации из самого факта её загрузки.

Для DT задайте `stateRole`: `initial` для состояния до feature, `failure` для состояния после ошибки либо `checkpoint` для промежуточной точки. При неизвестном происхождении оставьте `unspecified`. В `kot_run_start` передайте полученный `environmentId`. Повторное использование уже запускавшейся базы не считается восстановленным начальным состоянием. Для подтверждения исправления создайте свежую копию начального DT.

Для защищённого DT в `agent.clientProfileId` укажите ID сохранённого профиля с соответствующим пользователем. Операции Designer требуют установленной подходящей платформы. Для сохранения контрольной точки и обновления базы сначала закройте её клиент. Работа с несколькими подключёнными базами требует явного выбора: KOT не подменяет их молча.

Для инструментов чтения прикладных данных Vanessa может потребоваться клиентское расширение VAExtension. `kot_environment` с `action: prepare_tools`, `environmentId` и локальным `source` устанавливает его в выделенную базу при закрытых клиентах. Принимается только официальный CFE VAExtension 1.43 из релиза Vanessa `.47`, сверенный с закреплённым SHA-256; произвольный CFE этим маршрутом не загружается. После установки перезапустите клиент и проверьте реальный запрос: установка сама по себе не подтверждает доступ к данным. Пароли для Designer берутся из выбранного локального профиля либо ранее подготовленного в текущем сеансе клиента этой базы.

При полном запуске СППР KOT сохраняет имя клиентского профиля из собранного JSON и подставляет выделенную базу. Подключение выполняют начальные шаги теста. Учётные данные берутся из выбранного сохранённого профиля либо из настроек самого теста; модель их не получает. Для пробы с середины KOT подключает подготовленный клиент до выполнения шага. Несколько неоднозначных клиентов требуют явного выбора сохранённого профиля.

Если язык с кодом `ru` в конфигурации имеет другое техническое имя, передайте `languageName`, например `Russian` для 1cDrive. KOT выгружает проверенное расширение, меняет только имя заимствованного языка и загружает его обратно в эту же выделенную базу. Имя следует брать из метаданных конфигурации. Неудачная проверка CFE до запуска Designer не портит базу; после незавершённого изменения конфигурации требуется новая копия.

## Разобрать архив CI

Выполните **Агент: импортировать архив падения CI** либо передайте агенту доступный путь для `kot_ci_import`. Выбранный через диалог ZIP разрешается для чтения в текущем сеансе. Для программного чтения внешнего архива настройте `agent.allowedRoots`.

Импорт сохраняет архив в виде отдельного расследования с перечнем распакованных файлов и контрольными суммами. DT распаковывается потоком; его бинарное содержимое не отправляется модели. Поддержаны ZIP/ZIP64 с методами Store/Deflate и именами ASCII/UTF-8, до 20 000 записей и 64 GiB распакованных данных. Ссылки, шифрование, опасные пути и коллизии имён отклоняются.

Желательный состав архива: журнал шагов и ошибка, исходники или точные Git-ревизии, feature и карта сборки, параметры окружения, снимки, DT до feature и после ошибки. Специальный манифест не обязателен: агент читает инвентарь и доступные журналы. Названия `before/after` не доказывают время захвата; происхождение снимков должно быть известно из CI.

После импорта запросите `kot_investigate`: агент изучает точные исходники, восстанавливает отдельную базу, исследует доступные данные и проверяет гипотезы. Импортированные исходники, журналы и тексты считаются данными расследования, не инструкциями агенту.

## Правки и продолжение

`kot_repair_propose` сохраняет объяснение, основания, базовые SHA-256 и тексты до/после. `kot_repair_apply` сверяет их с актуальными сохранёнными файлами. Сгенерированная feature обновляется сборкой из исходника.

Для длинного исходника вместо полного `text` передайте `edits` с точными `search`/`replace` и при необходимости `occurrence`. KOT применяет эти замены к проверенной SHA-256 версии файла и сохраняет остальные строки и окончания строк.

Политика задаётся в настройках расширения:

| `agent.repairPolicy` | Поведение |
|---|---|
| `read-only` | Каждая правка требует решения пользователя |
| `tests` | Небольшие изменения строк действий теста и новые тестовые исходники могут применяться автоматически; продуктовые изменения согласуются |
| `all` | Разрешены автоматические продуктовые правки в настроенных исходниках конфигурации |

Изменения существующих assertions, таблиц ожиданий, тегов, структуры и BSL теста требуют отдельного решения. Команда **Агент: рассмотреть предложенное исправление** открывает diff и позволяет одобрить либо отклонить предложение. Это проверка известных рисков; общая семантическая эквивалентность тестов автоматически не доказывается.

После одобренного продуктового исправления обновление выделенной базы из тех же исходников допускается с `repairId`. Для CF либо несвязанных изменений используйте политику `all` или штатный ручной маршрут обновления.

Для подтверждения продуктовой правки передайте её `repairId` при установке из `sourceKind: sources`. KOT сверяет хеши исправленных файлов до и после Designer и связывает успешную установку с базой. Контрольная точка сохраняет это происхождение и SHA-256 DT; восстановленная из неё копия наследует сведения только при совпадении хеша. Для свежего проверочного запуска укажите `stateRole: initial`. Успех на прежней конфигурации, другой базе либо после обновления без привязки к правке не подтверждает исправление конфигурации.

`kot_repair_verify` пересобирает затронутые тесты и запускает полную проверку. Исправление получает признак подтверждения только после успешного полного запуска на свежем начальном состоянии и совпадения сохранённых снимков исходников с применённой правкой. Состояние проверки и ссылки на прогоны доступны в операции исправления и отчёте.

Для длинных feature доступны `mode: step` и `mode: fromLine`. Укажите строку исходника и `preconditions`: как восстановлены переменные, форма, данные и почему повтор допустим. Для вложенного YAML можно указать `probeSource`. При нескольких соответствиях выберите конкретный `occurrence` из возвращённых вариантов. Устаревшая карта сборки не используется.

DT содержит сохранённую базу. Для повторения участка необходимо восстановить доступные предусловия; BSL-стек, открытые формы, незаписанные данные и типизированный контекст не восстанавливаются автоматически. Частичный успешный запуск сохраняется как probe и не подтверждает всю feature.

Workflow `kot_resume` задаёт агенту порядок восстановления длинного теста. Сначала он проверяет ревизию исходников и конфигурацию базы: начальный DT от develop нужно обновить до ветки стори на отдельной копии. Затем читает собранную feature, карту вложенных вызовов и журнал от начала до падения, находит последние фактически выполненные присваивания переменных, учитывая условия, циклы и повторные присваивания. Для нужных оставшейся части переменных фиксирует имя, область, тип, источник и значение; строки записывает через `kot_variables` и читает обратно. Ссылки и вычисляемые значения восстанавливает типизированным шагом или чтением базы, а не подстановкой представления.

Агент заново подключает нужного пользователя, открывает сохранённые объекты и проверяет форму, вкладку, текущую строку и эффекты уже выполненных действий. Если объект не был записан, выбирает последнюю стабильную точку до его создания и повторяет создание и заполнение; переход в отсутствующую форму недопустим. Перед повторением проведения, платежа или создания документа проверяет, что действие не создаст дубль. Неподтверждённые предусловия требуют более ранней контрольной точки либо полного старта. После пробы предусловий запускает оставшуюся часть, отслеживает весь выбранный набор и сохраняет, какие шаги восстановлены, повторены и остались непроверенными.

Причину несовпадения агент отделяет от ожидаемого поведения. Подтверждённое разработчиками изменение порядка колонок требует актуализации эталона с сохранением проверок значений; само падение старого MXL не обосновывает откат конфигурации. Решение пользователя и его источник сохраняются в расследовании.

`kot_run_reconcile` позволяет сверить неизвестный результат с живой Vanessa, если сохранён полный успешный ответ с идентификатором прогона. Проверяются завершённые результаты, состояние менеджера, путь и SHA-256 исполненной feature. Прежний `unknown` сохраняется для аудита. Инструмент не повторяет тест и не подтверждает результат по одному сообщению агента; при несовпадении статус остаётся `unknown`. Сверку выполняйте до закрытия менеджера или следующего запуска, пока результаты доступны.

## Проверить стори и подготовить документы

- `kot_story`: критерии приёмки, роли, данные, граничные/негативные проверки, работа с реальным UI без готовой feature, наблюдения и воспроизведение дефектов. Для человека тот же план служит маршрутом ручной проверки.
- `kot_review`: User Story, полный релевантный контекст diff конфигурации и тестов, проверка ожиданий, подготовка тест-плана и набора регрессии.
- `kot_generate`: существующие примеры и определения, исследование формы, новые сценарии с сохранёнными описаниями, сборка, запуск и исправление. Описание заполняется для каждого нового главного/вложенного сценария, процесса и самостоятельной feature: назначение, предусловия и данные, основные действия, ожидаемые результаты. Для inline-описаний и feature текст включается в первоначальное предложение исходников; для v3 агент сохраняет его через `kot_scenario_description` до финальной сборки и полной проверки. После исправлений описание сверяется с итоговым сценарием; отсутствие сохранения отражается в отчёте.

Команда **Агент: создать задачу тестирования стори** использует выделенный текст редактора либо введённую стори. Через `kot_task_create` также создаются задачи ревью, генерации и расследования. Критерии и ожидаемое поведение задаются явно; недостаточные бизнес-требования остаются вопросами.

`kot_task_record` различает предложенную проверку, наблюдаемое прохождение/ошибку, блокировку и невыполненную проверку. Наблюдения агента имеют происхождение `agent_assessment`; статусы исполнителя и артефакты сохраняются отдельно. Вызовы формы и снимки можно связать с задачей через `taskId`. Набор инструментов исследования данных определяется схемами подключённой Vanessa; отсутствие инструмента не заменяется выдуманным результатом.

`kot_report` и команда **Агент: открыть отчёт операции** показывают выполненные и оставшиеся тесты, наблюдения, причины правок, связанные прогоны и артефакты. История Git и точные снимки исходников позволяют объяснить изменения; подозрение на коммит подтверждается отдельным воспроизведением.

Длительный запуск продолжает выполняться при отключении агента. Для последующего автоматического разбора агент должен продолжить задачу. После перезапуска host незавершённые операции получают `unknown`; перед повтором необходимо сверить фактический сеанс. Остановка ожидания не считается доказательством остановки 1С.

## Вложенные сценарии и команды интерфейса

Для разбора вложенности агент использует `scenario.call_graph`: видит повторные вызовы, параметры, шаги процессов и неоднозначные ссылки. `scenario.references` показывает места использования через штатный поиск KOT. Это позволяет найти повторяющиеся проверки и оценить последствия правки; одинаковые названия сами по себе не означают дублирование, а статический граф не подтверждает прохождение теста.

`ui.commands` показывает маршруты команд интерфейса, в том числе из редактора и CodeLens. Через них доступны фильтры, представления, навигация, вставка ссылок/UID, настройки тестов и инструменты исследования форм. После команды редактора агент читает `ui.source_state` и сохраняет нужный буфер через `ui.save_source` с актуальной ревизией. Новые правки пользователя не перезаписываются.

Для массового исправления структуры есть `project.repair_changed/repair_all` с отчётом; перед записью проверяются доступ и несохранённые файлы. `debug.record_read` читает запись и сгенерированные шаги без очистки. `debug.stop/detach` управляют подключённой Vanessa; `kot_action_cancel` отменяет действие агента, а `project.repair_cancel` — пакет, запущенный из интерфейса. После остановки выполнение нужно проверить по фактическому состоянию.

Начальное подключение и собственные разрешения сервера, а также одобрение защищённых исправлений остаются пользовательскими действиями. Возможности конкретного сеанса Vanessa агент проверяет через `kot_runtime`.
