# Программный интерфейс ИИ-оператора KOT

Интерфейс запускается командой `kotTestToolkit.agent.start` либо `kotTestToolkit.agent.enabled`. Первый вариант работает с активным доверенным workspace и локальным расширением VS Code. Стандартный stdio-мост поставляется как `out/agent-mcp.cjs`; самостоятельное выполнение всего KOT без extension host в этот контракт не входит.

## Протокол и операции

Сервер реализует JSON-RPC MCP с инициализацией, сессией, `ping`, `tools/list`, `tools/call`, `prompts/list`, `prompts/get` и завершением сессии. Поддерживаемые версии: `2025-11-25`, `2025-06-18`, `2025-03-26`. Используются JSON-ответы Streamable HTTP; постоянный SSE-поток не объявляется.

`kot_workflow` без `name` перечисляет процессы, с `name` возвращает те же инструкции из `agentWorkflows`, что и `prompts/get`. Для клиентов без MCP-prompts это обычный read-only инструмент. При запуске сервера поставляемый `res/agent/kot-testing/SKILL.md` копируется в `<runtime>/agent/skills/kot-testing/`; инструкции по установке находятся в практическом руководстве.

Каждый запрос проходит авторизацию, проверку Origin, доверия workspace, метода и входной схемы. Результаты инструментов возвращаются как текст и, где применимо, `structuredContent`; PNG — как изображение. Ошибка инструмента имеет `isError`, а отсутствие подтверждённого результата не становится `passed`.

Длительные операции возвращают ID сразу. `kot_operation` читает порцию событий по `offset/limit`; `kot_artifact` и `kot_source_read` читают текст по строкам. Текстовые файлы сканируются потоком с полным SHA-256, ограничением 512 MiB и ограничением размера строки; усечение явно отмечается. `kot_source_search` возвращает ограниченное число совпадений.

`requestKey` идентифицирует конкретный запрос. Повтор ключа с другими параметрами отклоняется. Новый эксперимент использует новый ключ. Статусы `failed`, `stopped`, `cancelled`, `unknown`, `completed` и `passed` имеют разный смысл: например, завершённая подготовка базы или создание отчёта не являются пройденным тестом.

В ответах состояния и операции массивы `steps` длиннее 20 строк содержат последние 20, `stepCount` и `stepsTruncated: true`. Сохранённая история не сокращается. Исполнитель записывает полные детали результата в артефакт `test-result-<id>.json`, который можно читать порциями через `kot_artifact`.

Запуск связывается со снимками исходников, Git-ревизией/diff, входами сборки и фактическим результатом. Порядок тестов сохраняется. Один исполнитель владеет сеансом; операции формы и клиента во время выполнения и захвата ошибки отклоняются. При перезапуске незавершённая операция помечается `unknown` и не повторяется автоматически.

Структурированные ответы Vanessa разбираются локально до 16 MiB текста: прежний предел 1 MB не вмещал полный результат длинной feature. `kot_run_reconcile` допускает сверку только одного неизвестного теста с сохранённым полным успешным ответом и `runId`. Проверяются live-результаты, состояние менеджера, путь и SHA-256 исполненной feature. Исходный результат сохраняется отдельным артефактом; событие `run_reconciled` связывает новые доказательства. Признаки начального состояния и полноты не повышаются при сверке.

После изменения сохранённого шага Vanessa `.47` может оставить пустую привязку к процедуре при корректном снипете; обычная перезагрузка не всегда устраняет отклонение до запуска. Такой результат сохраняется как `unknown`. Workflow `investigate` описывает отдельный маршрут полной проверки: `kot_manager` с `action: start` создаёт новый управляемый менеджер, затем используется свежая начальная копия базы. Новый менеджер не наследует переменные и контекст выполнения; частичное продолжение требует их реконструкции. Открытие и загрузка feature ожидают до двух минут в пределах общего таймаута соединения; автоматического повторного исполнения при таймауте нет.

## Границы

`kot_scenario_description` читает и сохраняет поле описания сценария. Агент изучает исходники и вложенные определения и передаёт готовый текст. `action: read` возвращает описание, место хранения и ревизию, учитывающую исходники (включая native-скрипт), описание и формат/ветку проекта. `action: set` требует `description`, актуальную `expectedRevision` и `requestKey`; запись проходит политику, проверку занятости и несохранённых изменений, сохраняется как взаимодействие с артефактом. Повтор ключа возвращает прежний результат. Для v3 используется общий `ProjectLibraryStore` с проверкой исходного описания внутри очереди записи; legacy и самостоятельная feature изменяются существующими редакторами полей. Другие метаданные и шаги сохраняются. `allowExecution: false` сам по себе не запрещает описание; запрет записи задаёт `repairPolicy: read-only`. Сохранённое описание отражает анализ агента и не служит доказательством выполнения теста.

`kot_launch_settings` читает либо изменяет только ключи языка `/L` и локали `/VL` в `Extraparams` активного профиля СППР. Изменение требует актуальной ревизии, разрешённого исполнения и `requestKey`, сохраняется как взаимодействие с артефактом до/после. Публикация параметров повторно проверяет состояние профилей в очереди сохранения, чтобы не перезаписать пользовательские изменения. Применение не означает успешную проверку: нужны пересборка, перезапуск клиента и новый прогон. Остальные параметры, учётные данные и строки в кавычках сохраняются.

- Новые операции имеют собственные runtime-каталоги и идентификаторы. DT не передаётся модели.
- `kot_environment(action: create)` после подготовки базы вызывает общий сервис регистрации в лаунчере 1С. Необязательный `name` задаёт имя записи; каталог базы остаётся в изолированном runtime. `result.launcher.registeredName` содержит фактическое имя: общий сервис добавляет суффикс при совпадении с другой записью. `result.launcher` и событие `launcher_registration` сохраняют отдельный результат регистрации; её отказ не инвалидирует готовую базу. `action: register` повторяет только регистрацию существующего готового окружения, наследует имя исходного запроса, если новое не задано, и обновляет результат. Существующая запись повторной регистрацией не переименовывается. Чужие пути и ID других операций этим действием не регистрируются.
- Корни доступа ограничиваются workspace, настроенными исходниками/рантаймом и `agent.allowedRoots`. Сравниваются реальные пути; приватные каталоги и файл авторизации не публикуются.
- Внешний путь может получить доступ до остановки сервера после отдельного подтверждения в нативном окне VS Code. Ответить на это окно через MCP нельзя; настройки прав не изменяются. Для ещё не созданного каталога проверяется реальный существующий предок; после решения путь проверяется повторно.
- Обновление и восстановление относятся к выделенным базам. Совместимость платформы и возможности Vanessa проверяются существующими адаптерами; универсальный BSL-отладчик и восстановление стека не заявляются.
- `kot_environment(action: prepare_tools)` устанавливает VAExtension 1.43 только из локального CFE с закреплённым SHA-256 официального релиза `.47`. Размер, формат и реальный путь проверяются до запуска Designer; компонент и источник сохраняются в операции. Произвольные расширения требуют другого маршрута обновления. Чтение данных подтверждается отдельным запросом после перезапуска клиента.
- Автоматическая правка теста ограничивается небольшими изменениями действий. Известные изменения поведения требуют решения пользователя, доступного через команду расширения, а не инструмент подтверждения самого агента.
- Для `prepare_tools` необязательный `languageName` сопоставляет заимствованный язык `Русский` с техническим именем языка `ru` в целевой конфигурации. Допускаются только идентификаторы 1С. Меняются три ссылки в выгрузке доверенного расширения; прикладные модули не переписываются. Если Designer уже начал изменение и не завершился, база блокируется для проверки до восстановления свежей копии.
- Для повторного входа в участок нужны актуальная карта, выбранное вхождение и описанные предусловия. Workflow `kot_resume` требует сопоставить ветку конфигурации, проследить выполненные присваивания до падения, восстановить типы/формы/данные и выбрать более раннюю стабильную точку для незаписанного объекта с учётом повторных эффектов. Успешный probe не подтверждает полный тест.
- Признак `verified` у исправления требует полного успешного прогона, свежего начального состояния и совпадения снимков изменённых исходников. Сам факт применения patch этого признака не устанавливает.
- Для конфигурации дополнительно требуется привязка установленной версии к `repairId`: хеши файлов до/после Designer, последнее обновление выбранной базы и зафиксированное при старте прогона происхождение. Обновление без привязки сбрасывает это доказательство; DT-копия наследует его через контрольную точку с проверенным SHA-256. Отказ до запуска Designer не портит прежнюю базу, прерванная начатая установка блокирует её проверку.
- Сервис предоставляет внешнему агенту инструменты и инструкции. После его отключения работает исполнитель, а reasoning возобновляется при продолжении задачи агентом.

Живая приёмка фиксирует конкретные версии 1С, Vanessa, компонентов и исходников отдельно от автоматических проверок. Официальный контракт транспорта: [MCP Streamable HTTP](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

## Менеджер баз и доступ агента

Для штатных операций KOT доступен каталог `kot_actions`: он возвращает идентификаторы действий и точные схемы аргументов. `kot_action_start` запускает выбранное действие и возвращает ID операции. Каталог ограничен явно зарегистрированными действиями; произвольный `executeCommand` не предоставляется.

| Возможность | Поддержка через MCP KOT |
| --- | --- |
| Создать файловую базу из пустой, DT, CF или исходников | `kot_environment`, `action: create`; только новое выделенное окружение |
| Назвать новую запись в лаунчере | `name` при `create` или новой регистрации; фактическое имя в `result.launcher.registeredName` |
| Повторить регистрацию без восстановления DT | `action: register`, только окружение агента |
| Выгрузить DT, создать новую копию из этого DT | `action: checkpoint`, затем `create` |
| Обновить конфигурацию из CF/исходников | `action: update`, только окружение агента |
| Подключить/закрыть клиента тестирования | `kot_client` и подготовка клиента при запуске |
| Перечислить все базы менеджера/лаунчера | Действие `infobase.list`, включая скрытые записи; учётные данные исключены |
| Переименовать запись, изменить путь, перенести или удалить базу | `infobase.rename`, `edit`, `reassign`, `move`, `delete`; штатные проверки занятости и подтверждения сохраняются |
| Восстановить DT поверх выбранной существующей базы, пересоздать её | `infobase.restore_dt`, `recreate`; только конкретный актуальный ID из каталога, с подтверждениями мастера |
| Выгрузить DT/CF, использовать установленный шаблон | `infobase.dump_dt`, `dump_cf`, `restore_template`, `update_template`; `infobase.create` открывает полный мастер |
| Платформа, ключи запуска, скрытие, порядок и регистрация | `infobase.platform`, `launch_keys`, `hidden`, `preferences_read/set`, `register/unregister` |
| Создать/изменить/удалить сохранённого клиента | `clients.list/save/delete`; ревизия каталога обязательна, секреты сохраняются в SecretStorage |

Граф вызовов статический: условия, циклы и значения переменных не доказывают выполнение. `truncated` означает достигнутый предел глубины/размера; для анализа дублирования проверок агент читает тела и сопоставляет предусловия и ожидания. Поиск ссылок возвращает страницы; их нужно дочитать. Несохранённые правки сначала проверяются через `ui.source_state`, затем явно сохраняются по ревизии.

В аудите `ui.commands` статус `available` указывает точное действие/инструмент, `user_control` — начальную настройку, подключение, собственный запуск/остановку сервера либо человеческое одобрение исправления, `internal` — служебный callback с публичным эквивалентом. Эти пользовательские и служебные операции не выдаются агенту как произвольные команды. `unmapped` явно сообщает о новой команде без маршрута API. Наличие маршрута не отменяет требования к состоянию проекта, платформе и возможностям подключённой Vanessa.

При `awaiting_agent` вызовите `kot_action_question(id)`, затем `kot_action_answer(id, questionId, answer, requestKey)`. В `answer` используется `text`, `choices` с ID вариантов, `paths` для файлов/каталогов либо `cancel: true`. Ошибка проверки ответа оставляет вопрос открытым; исправленный ответ получает новый ключ. Повтор запроса с прежним ключом не выполняет действие второй раз. `kot_action_cancel` запрашивает отмену; незавершаемые операции Designer/файлов могут закончиться до её обработки. После перезапуска хоста незавершённое действие становится `unknown` и автоматически не повторяется.

Состояние `completed` означает завершение штатного действия, а не прохождение теста. Проверяйте уведомления, возвращённые пути и чтение результата. Большие ответы сохраняются артефактом `action-result.json`. Подтверждение разрушительной операции допустимо только при разрешении пользователя на конкретное действие и цель. Для расследований по умолчанию используйте выделенные окружения `kot_environment`; прямые операции менеджера над существующей базой не заменяют доказательство установки продуктовой правки с `repairId`.

Параметры собственного доступа `kotTestToolkit.agent.*` меняются в мастере **Подключить ИИ** либо в интерфейсе настроек. Через API агент не может выдать себе разрешения, расширить свои корни или изменить собственную политику.

Операции с исходником требуют явный сохранённый `source`; номера строк `line/endLine` в каталоге начинаются с нуля. Изменение свойств требует актуальные `revision`, URI и версии документов из `properties.read`. Изменённые в редакторе связанные файлы блокируют запись. Пути ответов мастера проверяются по разрешённым корням; выбранная по ID известная база даёт временную область доступа только к её собственному каталогу. В журнале сохраняются хеши запросов и ответов, пароли не сохраняются.
