# Файлы проекта и владельцы данных

Исходники, общие сведения команды и локальный runtime имеют разный срок жизни. Не удаляйте sidecar как кеш и не коммитьте служебную ИБ как исходник теста.

## Исходники

```text
tests/
  main-test/
    meta.yaml                 # шапка, параметры и связи СППР
    scen.feature              # текст СППР-сценария
    meta.yaml.kot.yml          # сведения KOT об объекте
    test/900001001.yaml        # настройка самостоятельного запуска
    files/                    # вложения исходника
  nested-test/
    scen.yaml                 # альтернативный единый формат СППР
  process/
    process.yaml              # описание шагов процесса
    test/900001007.yaml        # только у главного процесса
  vanessa/
    smoke.feature             # самостоятельный тест Vanessa
    smoke.json                # пример соседнего JSON запуска
libraries/
  common.feature              # экспортные сценарии
  user-steps/                 # исходники пользовательских шагов
.kot/
  project.yml                # version: 3 — явный формат этой ветки
  groups/<id>.yml             # одна запись на группу
  imports.yml                 # завершённый импорт встроенных метаданных старого KOT
  history/<hash>.yml          # сведения об удалении/смене идентичности
  property-catalogs.yml
  test-numbering.yml
  parameter-profiles.json      # необязательные начальные профили
```

Это пример структуры, а не требование к именам всех папок. Корни задаются профилем. `scen.feature` рядом с `meta.yaml` — фрагмент СППР, поэтому от него не требуется заголовок самостоятельной Feature.

Идентичность сценария/процесса опирается на UID и исходник. Имя предназначено для вызовов и чтения; совпадение имён не разрешает неоднозначный UID или путь.

## Общие метаданные

`.kot/groups/<id>.yml` хранит группы, `property-catalogs.yml` — каталоги свойств и функций системы, `test-numbering.yml` — авторские серии и состояние выдачи кодов. Соседний `*.kot.yml` версии 2 хранит идентичность и метаданные объекта: группу, описание и категорию; прежний порядок читается только как начальное значение.

Старые центральные записи `.kot` и встроенные `KOTМетаданные` могут переноситься к исходникам. Запись защищена проверками UID, существующих данных и несохранённых документов. Неизвестные поля нельзя удалять под видом автоматической нормализации.

Файл `*.feature.kot-nested.json` содержит данные обратного преобразования вложенных/экспортных сценариев. Он не является runtime-кешем. В общей экспортной feature архив может хранить несколько записей; обратное преобразование затрагивает выбранную.

## Библиотеки пользовательских шагов

`step_definitions-src/<имя>/` содержит проект внешней обработки, а `step_definitions/<имя>.epf` — результат сборки. При создании из одиночного BSL KOT копирует его модуль в проект шаблона `TemplateEpfUF`; исходный файл сохраняется.

При создании проекта KOT добавляет недостающие экспортные переменные формы `Контекст` и `КонтекстСохраняемый`, которые Vanessa заполняет перед выполнением шага. Если переменные уже объявлены на уровне модуля без `Экспорт`, KOT добавляет этот признак. Реализации процедур и функций сохраняются. В ранее созданном проекте без этих объявлений добавьте их с директивой `&НаКлиенте`, затем пересоберите EPF и обновите библиотеки работающей Vanessa.

Рядом с исходным BSL файл `<имя>.bsl.kot-import.json` версии 1 хранит относительный `modulePath` созданного модуля. Пока модуль присутствует в индексируемой библиотеке, сохранённый исходник не создаёт второе определение шага. Изменения вносятся в созданный модуль; при удалении проекта исходник снова индексируется. Для проектов, созданных до появления этой связи, KOT восстанавливает её, если имя проекта совпадает с именем BSL и содержимое скопированного модуля полностью совпадает с оригиналом. Совпадение одного текста шага не объединяет независимые библиотеки.

В корне проекта обработки `.kot-library.json` хранит связь с EPF как относительный путь. Это позволяет выгрузить исходники в каталог с другим именем и затем пересобирать ту же EPF из строки шага или общей команды. Не изменяйте эту связь вручную при работающих операциях сборки.

Соседний с EPF файл `<имя>.epf.kot-build.json` версии 1 содержит SHA-256 исходников и двоичного файла. KOT создаёт его после успешной сборки или выгрузки. Несоответствие отпечатков, отсутствие EPF или неизвестная сборка блокируют использование шагов в IntelliSense и действиях вставки. Для готовой библиотеки из другого окружения пересоберите исходники либо выгрузите их из имеющейся EPF. Личные пароли в этих файлах не хранятся.

## Личные сведения

Favorites, раскрытие, выбор строк, личный порядок групп и элементов и привязки интерфейса хранятся в состоянии VS Code. Профили менеджера параметров и чувствительные поля клиентов используют SecretStorage. Коллекция профилей вместе с активным ID хранится под отдельным ключом, производным от URI первой корневой папки проекта. Открытие той же папки через `.code-workspace` не создаёт вторую коллекцию; окно без папки использует отдельную коллекцию. Прежний общий ключ сохраняется для явного импорта через меню профилей.

Экспортированный вручную JSON может уже содержать секреты — проверьте его перед добавлением в Git.

## Начальные профили проекта

Необязательный `.kot/parameter-profiles.json` задаёт переносимый начальный набор. KOT читает его только при отсутствии локально сохранённой коллекции этого проекта. Изменения в менеджере сохраняются в SecretStorage, имеют приоритет над начальным набором и не записываются в этот файл. Это позволяет поставлять примеры или шаблон проекта без перезаписи личных настроек.

Формат совпадает с коллекцией профилей версии 5: `version: 5`, `activeProfileId` и непустой массив `profiles`. У каждого профиля есть строковые `id`, `name` и массивы `buildParameters`, `additionalVanessaParameters`, `globalVanessaVariables`. Строки содержат `key`, `value`; для дополнительных параметров и GlobalVars также указывается `overrideExisting`. Массив или объект в `value` записывается как JSON-строка, как в менеджере. Активный ID должен присутствовать в коллекции. Некорректный файл вызывает предупреждение и чистый профиль, без наследования прежних общих настроек.

Полный пример — [профиль мастерской](../../examples/kot-workshop/.kot/parameter-profiles.json). Для проектных путей используйте относительные значения: `Libraries` — список через `|`, каталоги библиотек Vanessa — JSON-массив. Не добавляйте пароли и персональные подключения в общий начальный набор. Значения платформы, EPF Vanessa и компилятора по-прежнему настраиваются существующими средствами KOT/VS Code.

## Служебные файлы

По умолчанию runtime расположен в `.vscode/kot-runtime`; настройка `kotTestToolkit.runtime.directory` позволяет выбрать другой путь. Здесь создаются параметры компиляции, журналы, временные feature, отчёты и служебная ИБ. Это не то же самое, что `FeatureFolder` компилятора.

Компилятор может очищать свой каталог результата. KOT разводит конфликтующее расположение runtime и output, чтобы его служебные файлы не попадали под такую очистку. Сгенерированные результаты проверяйте отдельно от авторских `files/`.

## Хранение порядка и разрешение конфликтов

Порядок групп и объектов хранится в `ExtensionContext.workspaceState`: ключи `kot.projectGroupDisplayOrder.v1` и `kot.projectEntityDisplayOrder.v1` привязаны к корню проекта и разделу. Прежний `order` в sidecar читается как начальное значение; перетаскивание и поле «Порядок отображения (локально)» не меняют его на диске. Порядок шагов процесса остаётся частью исходника.

Новые тесты не дописываются в общий реестр. Маркер `.kot/imports.yml` фиксирует выполненный импорт встроенных метаданных старого KOT и меняется только при таком импорте. Удаление метаданных или смена UID создают отдельный tombstone в `.kot/history/`, чтобы прежние встроенные сведения не появились повторно. Файлы записываются с проверкой исходного состояния и откатом при ошибке.

Команда разрешения конфликтов читает стадии Git base/ours/theirs. Независимые поля объединяются, реальные конфликты требуют выбора, удаление против изменения тоже требует выбора. История импортов объединяется без потери ключей; списки имён учитывают удаления; функции системы сопоставляются по UID, серии — по префиксу, счётчики берут максимум. YAML с неизвестной схемой, дубликатами ключей или aliases отклоняется. Предложение применяется после просмотра diff и повторной проверки диска, редактора и индекса. Git staging не выполняется. Пользовательский Git merge-driver не устанавливается.

## Формат рабочей ветки

Обновление расширения не переводит проект на новый формат. Без `.kot/project.yml` с единственным полем `version: 3` действует совместимый режим: группы, описание, категория и порядок остаются внутри `KOTМетаданные` исходного YAML. Чтение проекта не создаёт sidecar и не удаляет старые блоки. Остаточные файлы новой схемы не включают её автоматически. Новые сценарии создаются в `scen.yaml`, даже если пользовательское предпочтение — `native`; автоматическая конвертация при сохранении не запускается.

Метка версии хранится в Git в той же ветке, что исходники и соответствующие изменения CI. Неподдерживаемая, конфликтующая или символьная метка не разрешает управляемую запись. Перед записью KOT повторно проверяет метку и состояние Git HEAD, поэтому разрешение из другой ветки не остаётся в кеше окна. При смене ветки пересканируются Менеджер тестов, экспортные библиотеки, пользовательские определения и самостоятельные feature. Профили параметров по-прежнему разделены между папками проектов.

Настройка путей, профиля и выполнения сама по себе не создаёт метку. Для существующего проекта включите в мастере **«Перевести эту ветку на формат KOT 3 — CI подготовлен»** и просмотрите план. Новые проекты мастера сразу используют формат KOT 3. При ошибке первичной подготовки KOT удаляет созданную этой операцией метку, сохраняя метку другой ветки или внешние изменения; во время импорта старые YAML-блоки сохраняются. Новые операции с общими группами и преобразованиями формата требуют перехода; редактирование прежних inline-метаданных остаётся доступным.
