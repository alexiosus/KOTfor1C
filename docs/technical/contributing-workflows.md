# Обработка документа и добавление возможностей

Этот документ помогает найти место изменения в KOT 3.0.0. Команды проверки и подготовка checkout описаны в [разработке](../DEVELOPMENT.md).

## Сохранение исходника

Входная точка — обработчики документа в [extension.ts](../../src/extension.ts). Учитывайте разные маршруты:

1. При сохранении обычного `scen.yaml` может сработать явно включённая миграция в парный формат. После успешной конвертации дальнейшая синхронизация относится уже к новому исходнику.
2. Для `scen.feature`/`meta.yaml` используется [синхронизация пары СППР](../../src/spprScenarioSync.ts): текст и объявления читаются совместно, но не записываются друг поверх друга.
3. Для единого YAML проверяется `ТипФайла`. Внутренние повторные сохранения и уже обрабатываемые документы защищены от рекурсивного запуска той же операции.
4. Сохранение неактивного YAML-сценария обновляет индекс и попадает в `pendingBackgroundScenarioFiles`. Тяжёлая нормализация не должна запускаться для всего проекта после каждого события.
5. У активного исходника сравниваются снимки имени, используемых параметров и вызовов. По включённым настройкам выполняются tabs → spaces, выравнивание таблиц/присваиваний и актуализация секций. Перезаполнение зависит от релевантных изменений или неполной структуры.
6. Правки документа, индекс и зависимые состояния сборки обновляются с учётом актуальной версии. Связанные сценарии и экспортные библиотеки также участвуют в актуальности артефактов.

Миграция старых метаданных в sidecar имеет собственные проверки. Не возвращайте безусловную запись `KOTМетаданные` по старым, удалённым настройкам.

## Пакетная обработка

**Repair changed scenarios** обрабатывает очередь изменённых файлов, **Repair all scenarios** — выбранный исходный каталог. Первая команда подходит после массовой замены в редакторе; вторая создаёт большую нагрузку. Команда отмены останавливает дальнейшую обработку в поддерживаемых точках.

Успешный статус `updated` означает фактическое изменение итогового текста. Пакетная обработка проверяет критичные секции; при небезопасном результате пытается восстановить исходный текст и сообщает об отказе. Не считать сам вызов `applyEdit` доказательством успешного исправления, не затирать несохранённые документы скрытой записью на диск.

Для изменения этого потока проверяйте активный и неактивный документ, внутренний повторный save, отмену, отказ записи и парный формат. Состояние `stale` должно обновляться и после конвертации исходника.

## Добавить команду

1. Найдите ближайшую по смыслу команду в `package.json` и регистрацию в `extension.ts` либо профильном модуле команд. Сохраните принятые контекст и способ отложенной загрузки.
2. Добавьте `contributes.commands`, локализованный заголовок в `package.nls.json`/`package.nls.ru.json`, меню и условие `when`, если действие должно быть видно из UI.
3. Зарегистрируйте handler и поместите disposable в `context.subscriptions`. Саму операцию держите в профильном сервисе; не дублируйте её отдельно для палитры, свойств и дерева.
4. Переводы runtime-строк добавляйте в `l10n/bundle.l10n.json` и `l10n/bundle.l10n.ru.json`, если они используются через `vscode.l10n`. Названия фактических файлов проверьте в [каталоге локализации](../../l10n).
5. Проверяйте URI, тип документа, наличие выделения и доступность сеанса до записи/выполнения. Состояние меню не заменяет проверку в handler.
6. Добавьте поведенческую проверку результата и отказа, затем выполните `npm run check`, `npm run compile` и `npm run docs:reference`.

Новый setting также требует соответствующего типа, scope и описания в manifest. Справочник документации генерируется из него; вручную исправлять только сгенерированный текст недостаточно.

## Добавить диагностику и исправление

В [scenarioDiagnostics.ts](../../src/scenarioDiagnostics.ts) найдите подходящий этап проверки и контекст документа. У диагностики должны быть стабильный код, понятное сообщение, severity и точный диапазон. Для парного формата используйте текст feature и её метаданные, не требуйте обязательного заголовка самостоятельной Feature от фрагмента СППР.

Quick Fix должен предлагать безопасную версионную правку. Проверьте исходную ошибку, корректный аналог без ложного срабатывания, отключение правила и поведение при изменении документа до применения действия. Если код должен появляться в выборе отключаемых проверок, обновите соответствующий enum/описания настройки.

## Добавить действие webview

Найдите пару frontend/host нужного инструмента: например `media/phaseSwitcher.js` и [phaseSwitcher.ts](../../src/phaseSwitcher.ts). Используйте существующий протокол `postMessage`, проверку сообщения, локализацию и модель состояния.

Сначала определите действие и результат host, затем отрисовку busy/ошибки/успеха. После асинхронного ответа сверяйте актуальные сеанс, выбор и версию; старый ответ не должен менять новый тест. Не пересоздавайте весь webview ради обновления одной строки: проверьте сохранность скролла, фокуса, раскрытия и введённого текста.

Тест должен запускать настоящий скрипт webview на контролируемой границе DOM/host и проверять пользовательское действие. Для визуальных изменений дополнительно проверьте реальное окно VS Code на узкой ширине и с клавиатуры.

## Если меняется мост 1С

Правка [BSL-модуля EPF-моста](../../res/formExplorer/bridge/KOTFormExplorerBridge.bsl) требует пересборки `KOTFormExplorerBridge.epf` штатным маршрутом сборщика, затем перезапуска связанных TestManager/TestClient. Проверьте manual/auto, Locator, таблицу и фактический snapshot. TypeScript-сборка сама по себе не пересобирает BSL-артефакт.
