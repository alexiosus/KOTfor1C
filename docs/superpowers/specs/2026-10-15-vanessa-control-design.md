# Управление Vanessa из VS Code

Дата: 2026-10-15, уточнено 2026-10-20. Спецификация управления Vanessa после UI, сохранённых Debug clients и продолжения интеграции СППР. Транспорт, подготовка служебной ИБ, управление, запись и диагностика реализованы; точные результаты живой приёмки и ограничения выбранной версии приведены в плане.

## Назначение

Подключиться к совместимому сеансу Vanessa, выполнить сохранённый feature с выбранного шага или один шаг, запросить остановку и увидеть фактическое состояние. Затем синхронизировать точки останова и связать выполнение с исходным YAML. Обычный Debug с сохранёнными клиентами остаётся самостоятельным способом запуска.

## Подтверждённая внешняя граница

Статическая перепроверка релиза Vanessa **1.2.043.45** и develop `167efad4f61ca227366264ea61f36ddaefcfba53` зафиксирована в [аудите](../audits/2026-10-14-vanessa-debug-control.md#перепроверка-2026-10-15). Реестр, MCP handlers и главная форма в этих двух версиях совпадают. Это не подтверждает версию выбранного пользователем EPF или установленного devkit.

| Действие KOT | Проверяемая capability Vanessa | Ограничение |
|---|---|---|
| Выполнить feature со строки | `run_scenario(mode=reloadAndRunFromLine, filePath, lineNumber)` | Сохранённый файл и исполняемый шаг; предыдущие действия подготовки пропускаются. |
| Выполнить с выбранного шага | `select_step` + `run_scenario(mode=fromCurrentStep)` | Новый запуск сбрасывает счётчики циклов; это не прозрачный Continue. |
| Выполнить один шаг | `execute_feature_step` | Проверять параметры реального `tools/list`; не подменять этим BSL step-over. |
| Остановить | `stop_scenario` | Ответ подтверждает запрос остановки, но не завершение текущего действия. |
| Состояние и результаты | state/results/editor tools | Ответы Markdown; idle и заголовок результата не доказывают полного успеха. |
| Точки останова | `manage_breakpoints(list/toggle/remove_all)` | Активная вкладка Vanessa Editor; list/toggle не привязаны к пути в запросе. |
| Клиенты | `manage_test_client_profiles` / `manage_test_client` | В проверенном add/edit schema нет настройки порта; обычный JSON и live profiles имеют разные возможности. |

Для управления нужен MCP devkit с его транспортом в базе менеджера и Vanessa в том же `/TESTMANAGER` сеансе. VAExtension в базе клиента расширяет возможности отдельных шагов/инструментов и не является общей зависимостью управления менеджером. VanessaExt и Vanessa Editor проверяются для тех действий, которым они нужны. Endpoint — streamable HTTP с `/mcp`. Порт задаётся явно при `runMcp;mcpPort=...`: README devkit и примеры Vanessa используют разные значения. Предпосылки и инструменты проверяются через `initialize`/`tools/list`, без предположения по одному номеру версии. [Общая инструкция](https://github.com/Pr-Mex/vanessa-automation/blob/1.2.043.45/docs/AI/index.md#быстрый-старт), [обработчики команд](https://github.com/Pr-Mex/vanessa-automation/blob/1.2.043.45/VanessaAutomation/Forms/MCPVA/Ext/Form/Module.bsl).

Не планируется изображать native BSL debugger: в проверенном реестре нет pause, continue, step-over, step-in или step-out. Обычный уже открытый сеанс без MCP endpoint не становится управляемым от смены launch JSON.

## Интерфейс

В меню Open Vanessa добавить **Подключиться к Vanessa** и **Запустить управляемый сеанс**. Attach выбирает ранее сохранённый локальный endpoint или новый адрес. В Test Manager показывать компактную строку подключения, доступные команды, состояние и Detach. Не добавлять ещё одну постоянную кнопку в каждую строку теста.

У сохранённого `.feature` команды редактора и контекстное меню предлагают «Выполнить с этого шага» и «Выполнить этот шаг». При первом запуске со строки коротко объяснить пропуск предшествующей подготовки; запомнить ознакомление локально. Кнопка Stop остаётся доступной во время выполнения. Отсоединение не закрывает чужой сеанс и не останавливает тест автоматически.

Управляемый запуск может использовать уже реализованный набор Debug clients. Изменение набора не меняет подключённую Vanessa само по себе; применение к live-сеансу — явное действие, доступное только для поддержанных инструментом полей. Отсутствующий port capability отображается как ограничение, а не silently игнорируется.

Уточнение пользователя 2026-10-17: MCP следует автоматически подготавливать в уже используемой служебной ИБ KOT, через существующий `ensureSharedStartupInfobaseReady` и отдельный компонентный provisioning. Подготовка MCP выполняется по требованию управляемого запуска; обычная сборка продолжает работать независимо. Установленные версии/хеши компонентов учитываются отдельно от шаблона служебной ИБ. Подготовка согласуется с параллельными запросами и работающими сеансами; база не пересоздаётся ради установки MCP. Для внешнего Attach сохраняется режим проверки без установки.

## Модель и транспорт

- `VanessaControlTransport`: initialize, listTools, callTool, cancel/dispose; ограничение времени ожидания, разрыв соединения и SSE проверяются отдельно. Поддержанный MCP SDK выбрать и зафиксировать при реализации по актуальной официальной документации.
- `VanessaControlSession`: endpoint, generation, capabilities, active feature identity, execution state (`unknown`, `idle`, `running`, `stopping`, `stopped`, `failed`), owned breakpoint set и pending run. Асинхронный ответ от прежнего соединения не меняет новую сессию.
- Изменяющие команды сериализуются. Долгий run не блокирует Stop и чтение состояния. Нельзя посылать `select_step` во время ожидающего run: реализация Vanessa хранит общий MCP task ID.
- Markdown ответы обрабатывает отдельный adapter для проверенной версии. Неизвестный формат даёт `unknown` и диагностическое сообщение вместо ложного состояния «успех» или «пауза». Не запускать управление по случайным совпадениям слов в тексте.
- Endpoint хранится локально, токены — в SecretStorage. По умолчанию loopback; удалённый endpoint требует явного выбора. Учетные данные, launch keys и бизнес-значения не копируются в общий журнал.

## Breakpoints

Сначала отдельные Vanessa breakpoints в сохранённом standalone feature. Нативный `Breakpoint` UI VS Code использовать лишь после проверки, что он не конфликтует с другими Gherkin/1C debugger extensions. На первом этапе допустим отдельный gutter decoration + команды toggle/list.

Перед синхронизацией активировать нужный feature, проверить его идентичность и прочитать list. Применить разницу текущего и желаемого наборов; после таймаута повторно прочитать list, а не повторять toggle вслепую. Не использовать remove_all на чужом сеансе. Остановка на breakpoint означает прекращение последовательности перед шагом; следующая команда называется «Выполнить с выбранного шага», пока отдельный live-тест не подтвердит более сильную семантику.

## YAML и source maps

До запуска из YAML нужен manifest сборки: hash включённых исходников/зависимостей и эффективного профиля, hash feature и `.str`, worker namespace, compiler identity при доступности. Время изменения файла само по себе недостаточно.

Карта использует feature line с индексом 1 и UID/строку тела сценария. Для VS Code: `yamlLine0 = body.startLine + sourceBodyLine1 - 1`. Обратный поиск даёт 0, 1 или несколько развёрнутых вхождений. При 0 действие недоступно; при нескольких пользователь выбирает конкретный вызов/процесс/вариант/часть. Устаревшая карта требует новой сборки. Текущая навигация к исходнику может оставаться доступной, но не служит доказательством безопасности запуска.

## Критерии готовности

1. Attach/Detach и capability gating проверены без доступа к живой базе через fake transport, затем на совместимом disposable окружении 1С.
2. Standalone run-from-line/one-step/stop/state работают в реальном сеансе; Stop не блокируется ожидающим run, ошибки/частичное выполнение не показываются как полный pass.
3. Toggle после таймаута идемпотентен, чужие точки сохраняются, выбран правильный feature.
4. YAML запуск принимает только свежую однозначную карту либо явный выбор вхождения.
5. Управляемый запуск автоматически подготавливает компоненты MCP в служебной ИБ KOT. При неподдерживаемой версии/ошибке установки отображается конкретная причина. Для внешнего Attach недостающие возможности диагностируются без изменения базы. VAExtension не блокирует команды управления менеджером.

## Уточнения пользователя: шаги и рабочие панели, 2026-10-17

### Прямое состояние выполнения

Для управляемого сеанса MCP становится источником состояния выполнения вместо разбора текстового файла лога. `run_scenario` отправляет progress N/M с общей строкой сообщения; текущий файл, строка, идентификатор и статус шага читаются через `get_vanessa_automation_state`, а подробные результаты — после выполнения. Progress сам по себе не содержит подтверждения pass/fail конкретной строки. Короткие шаги могут целиком пройти между снимками состояния; их результат подтверждается итоговыми данными. Не обещать недоступный upstream поток событий start/end/status для каждого шага.

Различать выбранную строку редактора, фактически выполняющийся шаг и подтверждённый результат. «Следующий шаг» не вычислять как line + 1: условия, циклы и вложенные вызовы меняют маршрут. В ручном линейном режиме следующая выбранная строка — намерение KOT, а не наблюдение за исполнителем. Прогресс/снимки/результаты связываются с поколением подключения и конкретным запуском; поздний ответ не меняет другой запуск.

### F11 и YAML до полной сборки

Пользователь запросил ручное выполнение нескольких шагов на F11. Предлагаемая семантика: в активном редакторе сценария F11 выполняет выбранный шаг, ожидает результат и только при успехе выбирает следующую допустимую строку; при ошибке остаётся на проблемном шаге. Повторные нажатия во время выполнения не создают параллельных команд. Команда действует контекстно и не перехватывает F11 других отладчиков. Это ручной шаг Gherkin, не BSL Step Into. Для условий, циклов, экспортных/вложенных сценариев и сохранения контекста между шагами нужна отдельная live-проверка.

В проверенном реестре `1.2.043.45` инструмент `execute_step_from_text` **отключён**; использовать его наличие в исходнике как capability нельзя. Для простого обычного Vanessa-шага внутри YAML можно подготовить служебный mini-feature и выполнить его через `execute_feature_step`, сохранив связь с исходной строкой. Таблица/docstring принадлежат шагу. Исходный YAML остаётся обычным документом с Undo/Auto Save; runtime-фрагмент не заменяет редактор временным документом. Нельзя молча подставлять произвольный параметр, терять относительные пути/вложения или выдавать конструкции компилятора за исполняемый Gherkin. Вложенные YAML-вызовы, параметры с вариантами и структурные блоки требуют корректного развёртывания фрагмента/сценария либо явной причины недоступности. Мини-фрагмент не подменяет полноценную .str-карту собранного сценария.

### Панели поверх одного подключения

- **Клиенты:** редактор подключений с шаблонами и выбором базы из Infobase Manager; общая модель с сохранёнными Debug clients. Секреты остаются в SecretStorage. Настройка и применение к живой Vanessa — разные операции; поля без live-capability, включая порт в проверенной схеме profiles, не теряются и не объявляются применёнными.
- **Переменные:** компактная панель runtime-контекста с обновлением, поддержанными типами значений, изменением/удалением и проверкой результата. Объявления YAML и реальные runtime-значения показываются раздельно.
- **Form Explorer:** сохранить существующую панель, подключив источник данных MCP. Составить карту соответствия текущих функций и MCP-инструментов, восполнить пробелы и только затем удалить прежний мост. Файловый snapshot не становится доказательством актуальности MCP-сеанса; общее представление формы используется и IntelliSense.
- **Запись действий:** start/stop через `user_actions_recording`, получение Turbo Gherkin и прямая нативная вставка у текущей каретки YAML/feature с правильным языком/отступами и Undo. По уточнению пользователя от 2026-10-20 обязательный предпросмотр отменён; конфликт версии проверяется во время самой вставки. При сокращённом ответе `.45` без признака записи пользователь разрешил без подтверждения выполнять Stop, сохранять прежний текст и начинать новую запись. Внешняя остановка снимает локальное состояние, когда MCP возвращает признак записи; при его отсутствии явный Stop остаётся идемпотентным. Неудавшаяся вставка не блокирует новую запись.
- **Диагностика:** состояние менеджера/клиентов, версии, ошибки шагов, снимки окна, журналы регистрации и создание локального диагностического пакета с очисткой секретов. Фактические требования VAExtension проверяются для конкретной операции.

Поиск шагов, Library/IntelliSense и локальная диагностика Gherkin уже существуют. MCP добавляет проверку именно загруженной Vanessa и её библиотек; повторный каталог или вторая реализация локального линтера не нужны. Панели реализованы в пределах проверенных capabilities `.45`; текущие границы и живые проверки зафиксированы в плане. Полная parity Form Explorer и точки внутри экспортных вызовов остаются открытыми.
