# Подключения Vanessa и шаги текущего элемента

Статус: предложение следующего этапа по вопросам пользователя от 2026-10-20/21. Описанный ниже новый интерфейс и узкий MCP-инструмент ещё не реализованы.

Дополнение 2026-10-21: для существующего `.45` в KOT реализован совместимый путь через активацию выбранного элемента и автоматический `full`-анализ: очередь последнего выбора, логическая отмена устаревшего запроса и кеш со сверкой сообщённого состояния. Это не новый узкий endpoint и не исключает затрат на анализ. Вывод Vanessa steps — readonly-поле со свободным выделением. Состояние остальных возможностей приведено в [матрице реализации](../audits/2026-10-21-vanessa-capabilities.md).

## Быстрые шаги текущего элемента

Проверены исходники Vanessa `1.2.043.45`, commit `a9625b83adfe0612da2adf750d82ca7993d73a70`:

- `Forms/MCPVA_Служебный/Ext/Form/Module.bsl`: схема `get_form_analysis` принимает форматы full/gherkin/elements/buttons/messages; отдельного current-element режима нет. `get_form_element_data` возвращает свойства элемента по имени, без Gherkin-шагов.
- `Forms/MCPVA/Ext/Form/Module.bsl`: `MCPДанныеИсследователяФормы` получает исследователь формы и результат чтения дерева; `MCPСформироватьОтветАнализаФормы` в full дополнительно вызывает `ПолучитьИзмененияФормыGherkin`. Шаги текущего элемента включаются только при full и включённом Gherkin.
- `Forms/ИсследовательФормы/Ext/Form/Module.bsl`: `MCPПолучитьРезультатЧтенияФормы` читает форму; ограничение глубины применяется при форматировании дерева. Уменьшить ответ — не значит исключить полный обход.

Следствие: нынешний KOT не может получить нативные шаги текущего элемента отдельным быстрым запросом в `.45`. `gherkin=false` потеряет нужную секцию. Скрытые клики по интерфейсу или выдача локальных шаблонов за ответ Vanessa не подходят.

Предлагается отдельный инструмент со следующими свойствами; имя `get_current_element_steps` здесь предварительное, такого публичного инструмента в проверенной версии нет:

1. Получить активного клиента, окно, форму и текущий элемент средствами тестирования платформы, без построения дерева всей формы.
2. Вызвать существующую генерацию шагов для этого элемента и языка Vanessa. У таблицы сохранить контекст текущей строки/колонки. Вернуть элемент и шаги одним ответом.
3. Сообщить явную причину, если активный элемент недоступен; не подставлять произвольный элемент из кэша.
4. KOT проверяет схему инструмента, клиента и поколение сеанса; запоздавший результат не вставляется в другой документ. Результат показывается в нижней панели, вставка остаётся отдельным действием.
5. Для старой Vanessa оставить явно обозначенный медленный full-запрос. Поставка изменённого EPF внутри KOT не требуется: предпочтительна поддержка в самой Vanessa с проверкой capability при подключении.

Новый инструмент должен проверяться на большой форме: время не должно зависеть от количества соседних элементов. Отдельно проверяются поле, кнопка, checkbox, колонка таблицы, смена окна и отсутствие активного элемента. Запрос всей формы для Generate form checks остаётся ожидаемо отдельным.

## Чтение результата внешней остановки записи

Live-проверка `.45` на собственном клиенте 2026-10-21 обнаружила второй пробел: первый `user_actions_recording(action=stop)` вернул записанные шаги, повторный — пустую запись. В исходниках `ЗаписьДействийПользователя` каждый Stop заново вызывает завершение записи, затем читает `Объект.СгенерированныйСценарий`. Это не read-only операция. `get_editor_state` возвращает исходник feature, а не отдельный результат записи.

После подтверждённой внешней остановки KOT оставляет результат в Vanessa и сбрасывает свою кнопку. Вставка после Stop из KOT работает через ответ первого Stop; автовставка после внешнего Stop остаётся недоступной. Если state-флаг отсутствует, надёжно определить внешнюю остановку нельзя.

Предлагается дополнить MCP неразрушающим чтением состояния и результата записи с идентификатором capture. Чтение не должно заново завершать запись или очищать буфер; Start должен принимать явное желаемое состояние вместо переключения. KOT сможет получать результат после остановки в обоих интерфейсах, проверять capture/client/session и вставлять каждую запись только один раз. Предварительное имя/действие read не считается существующей capability: включать его можно только после проверки реальной схемы новой Vanessa.

## Подключение менеджера

Основное действие — **Connect Vanessa**, рядом — **Connection settings**. Статус в нижнем баре остаётся единым. При одном доступном совместимом локальном сеансе подключаться автоматически; при нескольких дать выбрать. Если сеансов нет, предложить запуск управляемой служебной Vanessa. В настройках доступны Start managed, Attach, Disconnect и сведения об endpoint.

Play запускает тест с его параметрами; подключение к менеджеру само по себе ничего не выполняет. В текущей реализации только `runVanessa.executionMode=mcp` использует управляемый запуск: обычный process и пользовательский command template ещё существуют. Поэтому старый путь запуска сохраняется как совместимость в настройках. Переименование кнопки без разделения этих действий скрыло бы различие режимов.

## База → пользователи → клиенты Vanessa

В подробностях Infobase Manager добавить раздел **Vanessa test clients**. Каждая строка — пользователь базы и его профиль: имя клиента, пользователь, тип клиента, порт, дополнительные ключи. Пустой пользователь означает запуск без явно заданного пользователя. Пароли — только SecretStorage; список принадлежит локальному менеджеру баз. Существующие saved Debug clients используются как исходные данные для переноса, без второго хранилища паролей.

Галочки выбирают строки для действия; общий checkbox выбирает все строки базы. Выбор не запускает и не закрывает клиенты. Действия разделены:

- **Add to Vanessa** — создать отсутствующие профили; уже совпадающие оставить, конфликтующие показать для решения.
- **Connect** — добавить отсутствующие выбранные профили и подключить их; уже подключённые пропустить.
- **Disconnect** — отключить выбранные клиенты от менеджера. Закрытие клиентского приложения — отдельное явное действие.

Перед применением перечитывается список живой Vanessa. Сопоставление — по нормализованной базе, пользователю и типу клиента; одинаковое имя другого подключения не считается совпадением. Для неоднозначных профилей требуется выбор, чужой профиль молча не заменяется. Состояния «сохранён локально», «добавлен», «подключён», «не совпадает» и текущая операция видны в строке, фактический активный клиент отмечен отдельно.

После операции список перечитывается и только подтверждённые изменения получают новый статус. Если версия MCP не умеет применять поле, оно сохраняется локально и показывается как неприменённое. В частности, проверенная `.45` не предоставляет полный эквивалент настройки порта в profiles API: интерфейс не должен выдавать перенос всех полей за подтверждённый результат.

Порядок внедрения: согласовать этот интерфейс → переиспользовать модель saved clients в менеджерах баз → добавить выбор и сверку live-профилей → заменить старое главное меню Connect/settings, сохранив совместимый process-запуск в настройках.
