# [MCP] Получение подсказок и проверок отдельного элемента без анализа всей формы

Тип: **Расширение API / производительность**.

Проверенная версия: **Vanessa Automation 1.2.043.45**, исходники commit `a9625b83adfe0612da2adf750d82ca7993d73a70`. Новейший develop в рамках этого черновика не проверен; перед публикацией стоит проверить воспроизведение на актуальной версии.

## Задача

При подготовке и анализе тестов через MCP нужны два вида Gherkin для одного элемента формы:

- **Подсказки действий (`suggestions`)** — варианты шагов для работы с элементом: заполнить поле, нажать кнопку, выбрать значение. Это раздел «Часто используемые шаги для текущего элемента» исследователя формы Vanessa.
- **Проверки состояния (`checks`)** — шаги, проверяющие текущее значение или состояние элемента. Это эквивалент команды «Форма → Получить проверку текущего элемента формы в виде шагов» (`Ctrl+Shift+C`).

Сейчас подсказки можно получить через анализ всей формы. Отдельного MCP-эквивалента команды проверки только текущего элемента в проверенной версии не найдено. Общий запрос для одного элемента позволил бы решить обе задачи без лишнего обхода формы.

## Воспроизведение

1. Подключить тест-клиент и открыть большую форму с группами, полями и таблицами.
2. Активировать поле с заполненным значением. В UI выполнить «Получить проверку текущего элемента формы в виде шагов» (`Ctrl+Shift+C`) и сохранить результат для сравнения.
3. Вызвать `get_form_analysis` с `{"format":"full","compact":false,"max_depth":1}`. Сравнить раздел подсказок с исследователем формы и раздел проверки — с результатом `Ctrl+Shift+C`.
4. Отдельно вызвать `get_form_analysis` с `{"format":"gherkin"}`: результат относится ко всей форме, а не только к активному элементу.
5. Измерить время запроса `full` и сравнить с чтением одного поля через `get_form_element_data`.
6. Повторить `full` с `gherkin=false`: требуемый раздел подсказок текущего элемента тогда не возвращается.

## Ожидаемое и фактическое поведение

Ожидается запрос Gherkin для одного указанного либо активного элемента, с явным выбором подсказок действий или проверок состояния, без изменения фокуса в клиенте.

Фактически:

- `get_form_analysis(format=full)` выполняет анализ формы ради подсказок одного активного элемента. `max_depth` сокращает вывод дерева, но не исключает полный обход и построение Gherkin. `only_table/only_group` также не выбирают элемент для генерации подсказок или проверки.
- Публичная схема не позволяет передать `ТолькоАктивныйЭлемент` для проверки состояния, хотя соответствующая команда есть в UI.
- Нельзя запросить оба вида результата по имени элемента, полученному из дерева формы, независимо от текущего фокуса в тест-клиенте.

В контрольном замере на собственном клиенте с 1680 узлами полный анализ занял около 10,7 с, а чтение подробностей поля — около 89 мс. Это иллюстрация стоимости полного обхода, а не норматив производительности.

## Предложение

Добавить отдельный инструмент либо расширить существующий API. Например:

```json
{
  "element_name": "ИмяПоля",
  "mode": "suggestions"
}
```

Требования к контракту:

- `mode=suggestions` возвращает нативные подсказки действий исследователя формы только для указанного элемента.
- `mode=checks` возвращает проверку состояния этого элемента, эквивалентную штатной UI-команде. Для активного элемента можно переиспользовать генерацию с `ТолькоАктивныйЭлемент=true`, упорядочиванием колонок и переводом.
- При отсутствии `element_name` используется активный элемент клиента; при его явном указании фокус в клиенте не меняется.
- Запрос не строит дерево и Gherkin-состояние всей формы. Если узкая обработка какого-то вида элемента невозможна, ограничение сообщается явно.
- Вместе с текстом возвращаются имя элемента и идентичность клиента/формы, чтобы MCP-клиент мог определить смену контекста и не использовать устаревший ответ.
- Язык соответствует настройке генератора Vanessa; значения полей и пользовательские литералы сохраняются.

Название инструмента и параметров — предложение, а не описание уже существующего API.
