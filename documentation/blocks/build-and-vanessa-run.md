# Блок: Build and Vanessa Run

## Задача блока

Из набора YAML-сценариев получить готовые артефакты (`.feature` + `.json`) и запустить их в Vanessa Automation.

## Сборка

### Что делает сборка

- Читает выбранные в Test Manager главные сценарии и процессы.
- По выбранным чекбоксам автоматически формирует `Exceptscenario` или `Scenariofilter`.
- Запускает `СборкаТекстовСценариев.epf` для каждой запрошенной части сборки.
- Генерирует `.feature`, необязательные `.json` и карты строк `.str`.
- Дополнительно формирует соседний `*.combined.json`, куда KOT мержит `Additional Vanessa parameters`, `GlobalVars` и свои runtime-пути.
- Показывает уведомления о результате и дает быстрые действия (открыть файл/папку).

### Части сборки

Чтобы собрать весь набор по частям, задайте `ThreadsCount=3` или `ThreadTotal=3`, оставив `ThreadIndex` и `ThreadNumber` незаполненными. KOT запускает все три части с ограничением до двух одновременных процессов. При ошибке одной части остальные останавливаются, и сборка не считается успешной.

Для сборки только одной части задайте `ThreadIndex=2` (вторая часть) или `ThreadNumber=1` (тот же номер начиная с нуля). ThreadTotal имеет приоритет над ThreadsCount, ThreadIndex — над ThreadNumber.

Каждая часть собирается в отдельном runtime-каталоге. При нескольких частях итоговые артефакты находятся в `FeatureFolder/part-1`, `part-2` и т. д.; внутри сохраняются каталоги баз и, в режиме Drive, настроек тестов. Имена файлов разных частей не заменяют друг друга. KOT объединяет compile.txt и отчёты JUnit.

### Отчёт сборки

В меню стрелки рядом с «Собрать» выберите «Открыть отчёт сборки». При ошибке компиляции или предварительной проверки текущий отчёт открывается автоматически. В отчёте доступны код завершения и лог каждой части, список настроек из compile.txt, результаты компиляции из JUnit и ошибки СППР. Если источник удаётся однозначно определить по UID или коду, рядом показана ссылка на YAML. Координаты стека проверяются по тексту и объявлениям вложенных сценариев; ссылка ведёт в строку соответствующего исходника. Ошибки передачи неизвестного параметра ведут в его присваивание, когда оно однозначно найдено. При недостатке данных открывается исходник без предположений о строке.

`compile.txt` перечисляет настройки, которые пытались собрать. Результаты компиляции нужно смотреть в JUnit и ошибках СППР. Отсутствующий или повреждённый дополнительный отчёт обозначается явно. Отчёт KOT формируется и после неудачной сборки.

Ссылки задаются относительно папки самого отчёта: например, `../../tests/Parent%20scenarios/Test/scen.yaml#L163`. Markdown-просмотр VS Code открывает текущую копию файла на указанной строке без запуска обработчика протокола `vscode://`. Ссылка сохраняется при переносе всей структуры проекта между Windows и macOS. Если файл находится на другом Windows-диске, относительный путь невозможен: для него сохраняется локальная ссылка VS Code.

При повторном открытии через KOT ссылки старых форматов (абсолютные пути, `file:` и `vscode://file`) преобразуются в относительные. У обычного отчёта компиляции исходная папка определяется по ссылкам на `compiler-parts`, поэтому отчёт, созданный в Windows, можно открыть в соответствующей папке проекта на Mac без пересборки теста.

Сообщение `Compiler format compatibility` — статическая проверка ограниченного YAML-формата, который читает обработка СППР. Это не запуск компилятора. Отчёт перечисляет затронутые строки со ссылками и пояснениями: кавычки у скалярных значений, отступы кратно четырём пробелам, точный маркер `|`, неподдерживаемые комментарии и расширение `.yaml`. Например, `OrderOnTab: 1` и `Default: true` в старом блоке `KOTМетаданные` вызывают предупреждения о некавыченных значениях; после переноса блока в соседний файл эти строки удаляются из входа компилятора.

### Процессы

Процесс задаёт последовательность сценариев и вложенных процессов. Создайте его командой `KOT - Create process`, через меню создания или кнопкой `+` в заголовке группы Test Manager: выберите в меню «Процесс» (другой пункт — «Главный сценарий»). Укажите имя и числовой код, выберите сценарии или процессы, затем эталонную базу из ModelDBSettings и один из её профилей пользователей. Выбор базы и профиля использует тот же мастер, что и создание главного сценария. Если каталог баз пуст, доступны управление базами или явный ручной ввод.

KOT создаёт каталог `<код>/process.yaml` и связанную настройку `test/<код>.yaml` в ProcessFolder. Процессы отображаются в Test Manager и участвуют в выборе для сборки. Для добавления нажмите «Добавить шаги процесса» над разделом `ШагиПроцесса` в YAML либо выберите этот пункт в контекстном меню процесса в Test Manager. В списке сценарии отмечены иконкой файла, процессы — нумерованного списка. Можно выбрать несколько элементов. Для удаления и перестановки шагов используйте «Изменить шаги процесса» или команду `KOT - Edit process steps`. После добавления, удаления или перестановки номера блоков `ШагиПроцесса1`, `ШагиПроцесса2` и номера в существующих полях `ПолныйКод` соответствуют порядку шагов; UID шагов и ссылки на них сохраняются. Новые шаги наследуют параметры по умолчанию из вызываемых сценариев или процессов. Сам процесс, процессы со ссылкой обратно на него и процессы с уже существующими циклическими ссылками не предлагаются для вставки. Ссылки повторно проверяются после выбора. Индивидуальные значения можно указать в `ПараметрыШага` YAML; редактор порядка шагов сохраняет эти значения.

Компилятор объединяет ProcessFilter с фильтрами сценариев и настроек. Чтобы выключенный процесс не попал в сборку через включённый сценарий, KOT временно исключает его файлы настроек и восстанавливает их после сборки, ошибки или отмены. Описание процесса остаётся доступным для включённых процессов, которые используют его как подпроцесс. Для вложенных процессов KOT использует исключение выключенных сценариев и переводит ProcessFilter в эквивалентный отбор по кодам настроек: это обходит ошибку рекурсивного обхода фильтров в предоставленном компиляторе. Если код настройки совпадает с кодом настройки невыбранного процесса, сборка сообщает об этом совпадении; задайте уникальные коды. Явно указанный ProcessSettingsFilter сохраняет отбор всех настроек с указанными кодами.

Новые шаги со сценарием содержат поля `Сценарий*`, а шаги с подпроцессом — `ВложенныйПроцесс*`; пустые поля другого типа не добавляются. Существующие записи сохраняют пользовательские поля. Процесс и его настройки открываются в режиме YAML. Шестерёнка в шапке процесса открывает настройки по UID, при нескольких настройках предлагается выбор. Кнопки возле имени и кода изменяют их независимо, обновляют ссылки из других процессов и связанные настройки. Особые имя и код варианта настройки сохраняются. В настройке процесса доступны выбор связанного процесса, эталонной базы и профиля пользователя.

Зависимости учитывают шаги со сценариями и подпроцессами. В третьей колонке полной Библиотеки выберите процесс, чтобы увидеть его шаги. Перетащите строку за маркер слева: линия показывает место вставки перед или после другого шага. Можно переместить шаг в конец списка; с клавиатуры работают Alt+Вверх/Вниз. Новый порядок сохраняется в YAML с обновлением нумерации. Кнопка `+` над списком открывает мастер добавления, корзина в строке удаляет шаг. Удаление шага, на выходные параметры которого ссылаются другие шаги, требует сначала изменить эти ссылки. После изменения имени, кода или шагов требуется пересборка устаревшего feature.

Над `ШагиПроцесса` доступны обе команды: «Добавить шаги процесса» и «Изменить шаги процесса». В обеих Библиотеках «Главные сценарии» и «Процессы» — отдельные источники. Все типы записей имеют иконки; в полной Библиотеке рядом с группой показан тип записи: шаг Vanessa, пользовательский шаг, экспортный или вложенный сценарий, главный сценарий, процесс или feature.

В Test Manager главные сценарии и процессы находятся в отдельных сворачиваемых секциях. В каждой секции сохраняются группы из метаданных; одинаковое имя группы может встречаться в обеих секциях, при этом сворачивание и выбор строк работают независимо. Кнопка «+» секции создаёт соответствующий тип элемента, а «+» группы открывает выбор между главным сценарием и процессом с сохранением выбранной группы. Выбор для сборки, поиск, фильтры, избранное и связи с результатами остаются общими. Сворачивание секции сохраняется при обновлении панели.

В обеих Библиотеках контекстное меню и клавиша Delete удаляют локальные сценарии, процессы и самостоятельные feature. Главный сценарий удаляется с каталогом; процесс — с файлом описания и связанными по UID настройками, сохраняя другие файлы его каталога. У экспортного сценария удаляется только его блок, остальные сценарии в feature сохраняются. Файлы перемещаются в корзину; экспортный блок удаляется правкой документа. Перед удалением необходимо сохранить изменённые файлы и убрать внешние вызовы удаляемого элемента. Каталоги встроенных и пользовательских шагов Vanessa остаются доступны для чтения.

Процесс содержит ссылки на сценарии и подпроцессы; структурные ключи YAML остаются русскими по формату СППР. Английские шаги внутри сценариев поддерживаются. Компилятор выбирает английский язык итогового feature по `#language: en` в тексте первого сценария процесса, но в `ТекстПроцесса` не вызывает языковую нормализацию, которую вызывает для обычного сценария. Поэтому он оставляет русские заголовки и стандартные шаги подключения TestClient и закрытия окон.

При объединении результатов сборки KOT исправляет эти шаблоны у английских feature процессов: заголовки становятся `Feature`/`Scenario`/`Background`, подписи групп — `Scenario`/`Subprocess`, подключение TestClient и закрытие окон получают английскую форму. Вложенные директивы языка заменяются пустыми строками; число строк, BOM и переводы строк сохраняются, поэтому карты `.str` остаются действительны. Таблицы, docstrings, параметры и вложенные файлы сохраняются. Собственные шаги и проверки функциональных опций компилятор автоматически целиком не переводит; смешанный бизнес-текст требует доступных в Vanessa формулировок.

Назначение блоков параметров и тегов, порядок применения значений и примеры: [Параметры процессов и настроек](./compiler-process-parameters.md).

### Общий feature

При SeveralScenariosInOneFile несколько исходных сценариев могут попасть в один feature. KOT связывает артефакт со всеми его сценариями. Запуск любой такой строки выполняет весь feature; подсказка кнопки перечисляет его сценарии. Статус относится ко всему запуску, а изменение одного источника помечает весь общий артефакт устаревшим.

При CreateJson=false feature-файлы доступны для просмотра. Встроенный запуск Vanessa требует JSON; для запуска включите CreateJson либо настройте собственный commandTemplate.

Разделение путей:

- `FeatureFolder` из параметров СППР отвечает именно за выходные `feature/json` артефакты;
- `kotTestToolkit.runtime.directory` отвечает за служебный runtime KOT: `yaml_parameters.json`, build log, result file и временные папки;
- если runtime-путь KOT попадает внутрь `FeatureFolder`, KOT автоматически уводит свои служебные файлы в соседнюю безопасную папку `*.kot-runtime`, чтобы не конфликтовать с очисткой каталога со стороны СППР.

### Важные действия в UI

- `Build tests` (`Собрать тесты`) как split-button:
  - основное нажатие сразу запускает сборку;
  - в выпадающем меню можно переключать активный профиль Менеджера параметров;
  - `Accounting mode` показывается там только при включенных 1C:Drive-элементах UI.
- `Cancel build` (`Отменить сборку`)
- `Open feature file(s)` / `Open folder` (`Открыть feature-файл(ы)` / `Открыть папку`) после сборки
- `Open JSON` в контекстном меню теста:
  - `Open built JSON` — исходный JSON от СППР;
  - `Open combined JSON` — итоговый JSON, который KOT использует для built-in запуска Vanessa.

## Запуск Vanessa

### Способы запуска

1. Иконка запуска рядом со сценарием.
2. Верхняя кнопка `Open Vanessa` в Test Manager с выбором сценария.
3. Команда `KOT - Open scenario in Vanessa (manual debug)` для ручной отладки уже собранных сценариев.

В UI доступны два режима:

- автоматический прогон;
- `manual debug` — открыть Vanessa для интерактивной отладки без автозакрытия.

### Статусы запуска

- `running`
- `passed`
- `failed`
- `stale`

### Выбор и подготовка тестовой базы

- Перед built-in запуском Vanessa можно:
  - переиспользовать последнюю выбранную ИБ для этого сценария;
  - взять путь из уже собранного JSON;
  - выбрать существующую ИБ из общего списка менеджера баз (`launcher`, `runtime`, `snapshot`, `manual`, `workspaceState`);
  - указать существующую файловую или серверную ИБ вручную;
  - создать новую файловую ИБ.
- В picker-е выбора ИБ KOT скрывает базы, помеченные как hidden в `KOT Infobase Manager`, поэтому служебные runtime-базы не мешают в обычных сценариях запуска.
- Для generated JSON KOT ожидает, что launch-база уже была задана в параметрах СППР (`LaunchDBFolder` / `TestClientDBPath` / `InfobasePath` / `TestClientDB`):
  - KOT не создает пустой блок `КлиентыТестирования`, если СППР сам его не собрал;
  - если launch-настройки отсутствуют, правильный путь — заполнить параметр в Менеджере параметров и пересобрать тесты.
- Команда `KOT - Open Infobase Manager` открывает отдельную панель управления ИБ:
  - единый список обнаруженных баз;
  - создание, пересоздание, восстановление/выгрузка `DT`, обновление конфигурации, регистрация в launcher и быстрый переход к логам;
  - per-base ключи запуска, переименование, перенос каталога базы и полное удаление файловой ИБ;
  - те же сохраненные пути и метаданные затем используются и в picker-е built-in запуска Vanessa.
- Для выбранной ИБ доступны опциональные шаги подготовки:
  - для существующей ИБ можно выбрать режим пересоздания с нуля в той же папке перед дальнейшей подготовкой;
  - восстановление из `DT` при создании новой или пересоздании существующей ИБ;
  - обновление конфигурации из `kotTestToolkit.formExplorer.configurationSourceDirectory`;
  - обновление конфигурации из выбранного пользовательского `.cf`.
- Диалог восстановления `DT` устроен так:
  - `No DT restore`;
  - `Restore from etalon DT` — если в `test.yaml` указана эталонная база и для нее найден `DT` в `ModelDBSettings` / `bases.yaml`;
  - `Restore from another DT`.
- Последняя выбранная ИБ запоминается на сценарий и предлагается повторно.
- При создании новой ИБ папка выбирается через системный диалог, затем запрашивается имя базы для launcher 1С, и после успешного создания база автоматически добавляется в launcher.
- Для новой ИБ и для режима пересоздания существующей ИБ обязательно нужно выбрать хотя бы один шаг подготовки (`DT` или обновление конфигурации), иначе запуск блокируется как для пустой базы.
- Если выбрано `Keep current infobase contents`, KOT сохраняет текущие данные и сразу предлагает необязательное обновление конфигурации. Восстановление из `DT` заменяет данные базы, поэтому для него выберите `Recreate infobase from scratch` или создайте новую ИБ.
- Во время подготовки показывается пошаговый progress notification: создание ИБ, восстановление из `DT`, обновление конфигурации.

### Логи

- Отдельный run-лог на сценарий.
- Test Manager автоматически отслеживает свежие изменения/появления run-логов в `kot-runtime/vanessa`:
  - старые лежащие файлы не считаются активным прогоном;
  - если старый лог перезаписан новым прогоном, статус подхватывается заново;
  - первое одиночное обновление на старте можно отфильтровать, чтобы не подхватывать случайный ручной шаг;
  - если после автоподхвата лог перестал обновляться и не завершился штатно, трекинг снимается по таймауту неактивности;
  - при успешном сопоставлении имени/содержимого лога со сценарием статус в панели обновляется автоматически.
- `Open run log` (`Открыть лог запуска`) открывает файл run-лога в редакторе.
- Live-режим для сценария открывает `feature` на текущем выполняемом шаге.
- Output панель не открывается автоматически при старте прогона, если отдельно не включен `kotTestToolkit.runVanessa.showOutputPanel`.
- При падении в уведомлении и hover доступны быстрые действия для run-лога.
- Для внешних серверных прогонов доступен трекинг по содержимому run-лога:
  - старт из контекстного меню открытого `feature` (выбор файла лога) или из открытого `.log`;
  - поддержка нескольких логов на одну `feature` с быстрым переключением активного;
  - остановка трекинга из контекстного меню `feature`;
  - при старте из `.log` автоматически открывается связанный `feature` (по `Feature: ...` в шапке).
- Для внешнего трекинга ошибка фиксируется по строке `Failed:`.

### Подсветка и переходы по шагам в `feature`

- Во время выполнения шага:
  - текущая строка шага подсвечивается;
  - пройденные строки подсвечиваются зеленым;
  - при ошибке строка шага подсвечивается красным.
- Есть автосопровождение текущего шага с временной разблокировкой при ручной прокрутке.
- Переход к вложенному сценарию из feature и переход к упавшему шагу используют `.str`, если в нём есть точное соответствие: открывается строка внутри `ТекстСценария` по UID. Если карты или записи нет, сохраняется прежний переход по имени сценария либо к строке feature. Компилятор может записать неполную карту общего feature, поэтому KOT не угадывает отсутствующие строки.
- Для упавшего шага в hover доступны действия:
  - `Open run log`;
  - `Open failed nested scenario`.
- Подсветка шага сохраняется до изменения `feature`-файла или до пересборки артефактов.

### Shared startup-ИБ

Встроенные сценарии запуска и сборки используют общую легковесную startup-ИБ:

- она прогревается расширением автоматически;
- переиспользуется между `СборкаТекстовСценариев` и Vanessa;
- не требует отдельной legacy-настройки пути к пустой ИБ;
- на Windows KOT восстанавливает startup-ИБ из `KOTStartupTemplate.dt`, поставляемого в расширении, чтобы избежать предупреждения безопасности при первом запуске;
- запуск не требует прав администратора Windows, если есть обычные права записи в рабочий каталог проекта.

`KOT Form Explorer` использует отдельную builder-ИБ и не влияет на легкость startup-окружения для запуска тестов.

## commandTemplate: когда использовать

Используйте `runVanessa.commandTemplate`, если нужно:

- полностью контролировать командную строку запуска;
- встроиться в корпоративный launch-скрипт;
- добавить специфичные флаги/обвязку процесса.

Плейсхолдеры:

- `${scenarioName}`: имя запускаемого сценария (из `ДанныеСценария.Имя` выбранного теста).
- `${scenarioNameQuoted}`: имя сценария в quoted-виде для shell.
- `${featurePath}`: абсолютный путь к `.feature` выбранного сценария из результатов последней сборки.
- `${featurePathQuoted}`: путь к `.feature` в quoted-виде для shell.
- `${jsonPath}`: абсолютный путь к JSON, который будет использоваться для запуска. Для built-in launcher это обычно `*.combined.json`, если он доступен.
- `${jsonPathQuoted}`: путь к `.json` в quoted-виде для shell.
- `${workspaceRoot}`: абсолютный путь к корню открытого проекта в VS Code.
- `${workspaceRootQuoted}`: путь к корню проекта в quoted-виде для shell.

Если шаблон пустой, используется built-in launcher расширения.

Команда `KOT - Open scenario in Vanessa (manual debug)` всегда использует built-in launcher и не применяет `runVanessa.commandTemplate`.

Повторяющиеся диагностические сообщения Test Manager о фазах, checkbox state и сообщениях webview выводятся только при `KOT → Output: Advanced Logging`. Они описывают обновление интерфейса, а не обнаружение новых файлов. Одинаковые состояния артефактов не отправляются в тот же webview повторно; реальные изменения и новое открытие панели продолжают обновлять интерфейс.
