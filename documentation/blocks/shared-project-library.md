# Общая библиотека проекта

Группы KOT хранятся в `.kot/groups.yml` проекта. Порядок элементов, описания, категории и принадлежность к группе — в файлах рядом с исходниками тестов. Test Manager и обе Library используют одни объекты. Пустые группы сохраняются после закрытия окна и удаления последнего участника.

Каталоги проектов, уровней отчёта, категорий, ответственных и функций системы хранятся в `.kot/property-catalogs.yml`. Функции находятся в разделе `systemFunctions`, каждая запись содержит `name` и `uid`; первая запись используется по умолчанию при создании сценария. Панель свойств, мастера сценариев, обычные настройки VS Code и менеджер функций используют этот общий файл. При старте KOT переносит явно заданную старую настройку `newScenarioDefaults.systemFunctions` в отсутствующий раздел функций с сохранением UID. Открывать сценарий для этого не нужно. Существующий общий каталог, включая пустой, имеет приоритет.

Добавьте `.kot/property-catalogs.yml` в Git вместе с другими объектами KOT. Коллегам достаточно получить этот файл из репозитория — вручную повторять список функций в настройках VS Code не требуется.

## Редактирование в обычных настройках VS Code

1. Откройте настройки (`Ctrl+,`, на macOS `Cmd+,`) и найдите **Каталоги проекта и нумерация**. Можно искать `@ext:AlexeyEremeev.kot-test-toolkit catalogs`.
2. Выберите вкладку **Workspace**, а в рабочем пространстве с несколькими проектами — вкладку нужной **Folder**. **User** показывает личные значения, поэтому пустая таблица с пометкой **Modified in Workspace** не означает, что общий каталог потерян: переключитесь на Workspace. Внешний самостоятельный корень тестов нужно открыть как папку рабочего пространства, чтобы увидеть его каталоги в настройках.
3. В **Catalogs: Projects / Responsibles / Report Level1 / Report Level2 / Categories** добавляйте и удаляйте имена кнопками обычного списка. Это справочные значения, а не команды переименования существующих тестов.
4. В **Catalogs: System Functions** ключ — имя функции, значение — её UID. Для новой функции оставьте значение пустым: KOT создаст UID и покажет его в таблице. При изменении имени существующей функции сохраните UID.
5. В **Numbering: Series** ключ — шестизначный префикс, например `000012`, значение — имя тестировщика. Автор также попадёт в каталог ответственных. Личный префикс задаётся отдельно, во вкладке **User**, в **Numbering: Prefix**.

Если начать заполнять общий каталог в **User**, KOT предложит **Перенести в проект** или **Открыть настройки проекта**. Автоматического переноса нет: при закрытии уведомления введённые значения остаются в User. Явный перенос добавляет их к каталогу текущего проекта, сохраняет существующие записи и счётчики, затем удаляет успешно перенесённые значения из User и открывает настройки проекта. В workspace с несколькими папками используется проект активного редактора; если он не определён, KOT предложит выбрать папку. При старте такое же предложение доступно для записей, оставшихся в User после предыдущей неудачной попытки сохранения.

После подтверждения значения стандартной кнопкой настройки KOT сохраняет его в `.kot`. Изменения через панель свойств, менеджер функций или Git обновляют эти же поля настроек. Для отображения каталогов VS Code также сохраняет их представление в настройках проекта; источником общей истории остаются файлы `.kot`. При одновременном изменении одного поля в YAML и настройках KOT сообщает о конфликте и сохраняет обе версии. Сначала сохраните открытый изменённый файл каталога, затем повторите правку настройки.

Чтобы очистить список, удалите его элементы в настройках. Обычный **Reset Setting** сбрасывает представление настройки; существующие общие данные из `.kot` снова появятся в нём. Выданные номера в настройках скрыты, а серию с историей выдачи удалить нельзя.

## Использование

1. Откройте Test Manager. В заголовках Main scenarios, Processes и Standalone features при наведении или фокусе появляются «+» и «Новая группа».
2. Создайте группу кнопкой с папкой. «+» секции создаёт соответствующий элемент; «+» бизнес-группы предлагает главный сценарий или процесс.
3. Для существующего главного сценария или процесса нажмите «Изменить группу» рядом с заголовком YAML. В списке доступны и пустые группы; там же можно создать новую.
4. Описания и категории изменяются существующими действиями редактора. «Открыть метаданные проекта» рядом с именем открывает связанный объект KOT для просмотра и редактирования порядка и других полей.
5. Добавьте `.kot/groups.yml` и соседние `*.kot.yml` в Git вместе с исходниками тестов. После checkout/pull другие тестировщики получат те же группы, распределение, порядок, описания и категории. Изменения файлов обновляют панели и подсказки редактора.

## Файлы

- `.kot/groups.yml` — UID, названия, секции и порядок групп; состояние импорта и реестр уже известных сценариев.
- `scen.yaml.kot.yml` рядом с `scen.yaml` — метаданные сценария.
- `process.yaml.kot.yml` рядом с `process.yaml` — метаданные процесса.
- `sales.feature.kot.yml` рядом с `sales.feature` — метаданные standalone feature.

Имя включает полное имя исходника, поэтому `sales.yaml` и `sales.feature` в одной папке имеют разные файлы метаданных. Например:

```yaml
version: 2
identity:
  kind: scenario
  uid: "11111111-1111-4111-8111-111111111111"
metadata:
  groupId: "UID группы из .kot/groups.yml"
  order: 2
  description: "Проверка продажи"
  category: "Продажи"
```

Расширение `.yml` выбрано намеренно: штатный компилятор СППР рекурсивно читает `*.yaml` и использует собственный ограниченный YAML-парсер. Файлы KOT не должны попадать в его входы, особенно когда внешний каталог тестов содержит свой `.kot`.

При обычном расположении тестов `.kot/groups.yml` находится в корне workspace. Если настроенный каталог тестов расположен вне всех открытых workspace, он содержит собственный `.kot`. В общих файлах нет абсолютных путей запуска. Для сценариев и процессов используется UID; при отсутствии UID — путь исходника. Для feature используется путь, а runtime-идентичность и избранное продолжают использовать URI. Путь определяется расположением соседнего файла и не записывается в него: при переносе папки теста внутри проекта метаданные переезжают вместе с ней. Переименование исходника средствами VS Code переносит соседний файл; при переименовании вне VS Code перенесите его тоже. При переносе между проектами расширение связывает группу с реестром нового проекта.

Группа главных сценариев и процессов может быть одним бизнес-объектом с двумя секциями. Сворачивание и выбор в секциях независимы. Группы Standalone features имеют собственные объекты; одинаковое название не объединяет их с бизнес-группами.

## Перенос существующих данных

Первое сканирование переносит поддерживаемые поля `KOTМетаданные` и legacy `PhaseSwitcher_*`, а также локальные группы и порядок Standalone features. Старые центральные записи `.kot/metadata/*.yml` автоматически переносятся к исходникам после проверки. Если исходник не найден, запись остаётся на прежнем месте, а причина выводится в журнал расширения. Существующий корректный соседний файл имеет приоритет над центральной записью и локальными данными другого тестировщика. Новые, ранее неизвестные сценарии тоже импортируются; удалённые известные записи не восстанавливаются из старого YAML.

После безопасной записи соседнего `*.kot.yml` KOT удаляет перенесённый блок `KOTМетаданные` из исходника. Сначала сохраняются метаданные, затем меняется исходник; ошибка записи откатывает транзакцию. Открытый изменённый YAML не очищается до сохранения и следующего сканирования. Блоки с неизвестными полями и неоднозначный YAML сохраняются, чтобы не потерять пользовательские данные. Уже существующий соседний файл также позволяет очистить старый блок при следующем полном сканировании.

Штатные шаблоны, сохранение и исправление YAML больше не вставляют `KOTМетаданные`; устаревшие настройки автоматического восстановления блока удалены. Изменения KOT записываются в соседний `*.kot.yml`. Компилятор продолжает использовать штатные параметры, теги и шаги из исходников.

UID должны быть уникальны в пределах проекта для сценариев и процессов. При конфликте миграция останавливается до записи файлов и показывает конфликтующие исходники. Повреждённые YAML, конфликтные маркеры Git и неизвестные версии сохраняются без перезаписи и показываются как ошибка. Перед изменением библиотеки сохраните открытые редакторы `.kot/groups.yml` и `*.kot.yml`. Удаление теста через KOT учитывает соседние метаданные; при удалении папки они попадают в корзину вместе с тестом.

## Каталоги свойств

Общие списки свойств хранятся в `.kot/property-catalogs.yml`. Поле `responsibles` содержит имена ответственных; добавление через «Создать…» в поле **Ответственный** сохраняет имя в этот файл. После коммита и получения изменений коллеги увидят его в списке, даже если оно ещё не используется в YAML. Список также включает имена из заголовков сценариев и процессов текущего проекта. Это список ответственных за тесты, без учётных данных и связи с пользователями тестовой базы. Существующий `UIDОтветственный` из СППР сохраняется при выборе того же имени и очищается при смене человека, чтобы компилятор не получил старую ссылку вместе с новым именем.

При обычном сканировании сохранённые значения проекта, ответственного, уровней отчёта, категории и функции системы дополняют `.kot/property-catalogs.yml` и становятся доступны в **Project catalogs and numbering** в настройках VS Code. Дополнительного сканирования файлов для этого нет. Уже созданные вручную записи и UID сохраняются; повторный запуск не переписывает неизменившийся каталог. Авторов серий не выводят из поля `Ответственный`: оно может обозначать текущего владельца сопровождения. Серии задаются явно; при добавлении серии и выдаче номера учитывается максимальный существующий код. Ранее сохранённые серии автоматически не удаляются и не меняют владельца при смене ответственного.

Первичное сканирование передаёт миграции уже прочитанный текст старых блоков: повторный обход дерева YAML не нужен. Новые записи импортируются пакетом, а проверки и запись файлов выполняются с ограниченным параллелизмом. Наблюдатели ждут завершения транзакции и обновляют панели по итоговому состоянию. При перестановке меняются только метаданные элементов с новым порядком; очистка блоков и повторный разбор всего корпуса не запускаются. Проверки конфликтов и несохранённых изменений сохраняются.

## Личное состояние

Авторские серии и последнее выданное значение хранятся в общем `.kot/test-numbering.yml`; выбранная серия пользователя — локально. Подробности и проверка кодов для CI описаны в [создании сценариев](scenario-creation.md#авторские-серии-и-автонумерация).

Избранное, выбранные тесты, свёрнутые секции, логи, результаты сборки, учётные данные и выбранные локальные JSON запуска остаются локальными. Они не включаются в общие объекты KOT.

## Перетаскивание и порядок

По умолчанию группы идут по алфавиту, в том числе после переноса библиотеки из старой версии. В Test Manager группы и их содержимое переставляются перетаскиванием. Порядок групп сохраняется локально в workspaceState отдельно для проекта и секции и не меняет общие файлы. Другие тестировщики сохраняют свой порядок групп. Порядок элементов внутри группы и перенос элемента в другую группу записываются в соседние `*.kot.yml`; добавьте эти изменения в Git, чтобы они появились у коллег. Library и Test Manager используют одни и те же значения. Перенос между разными проектами или секциями не поддерживается; если состав группы изменился после начала перетаскивания, обновите панель и повторите действие.

Если групп ещё нет, новый главный сценарий или процесс попадает в служебную группу **Ungrouped** (**Без группы**). Её не требуется создавать в каталоге. При импорте сценарий без KOT-группы считается главным, если настройки запуска ссылаются на его UID в том же проекте; остальные сценарии остаются вложенными.

Для существующих тестов **Ungrouped** доступна через **Change group** в контекстном меню Test Manager и как пустая цель для перетаскивания, даже если в ней ещё нет тестов.
