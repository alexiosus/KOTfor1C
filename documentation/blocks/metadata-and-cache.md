# Блок: Metadata and Cache

## Задача блока

Обеспечить стабильную структуру метаданных сценариев и быстрое обновление состояния проекта без тяжелых полных пересканирований на каждое действие.

## `KOTМетаданные`

Общие группы хранятся в `.kot/groups.yml`, а порядок, описания и категории — в соседних с исходниками [объектах проекта `*.kot.yml`](./shared-project-library.md). Существующие YAML-блоки читаются для первоначального переноса и совместимости; после переноса объект проекта имеет приоритет. Создание, сохранение и исправление сценария больше не вставляют legacy-блок.

### Для чего нужен блок

- Хранит служебные данные сценария.
- Используется Test Manager для группировки и отображения.
- Хранит пользовательское описание сценария (`Описание`).

### Что делает расширение автоматически

- Поддерживает чтение legacy-тегов и стандартного формата `KOTМетаданные`.
- При первом сканировании переносит legacy-данные в соседний `*.kot.yml`.
- Сохраняет описание в объекте проекта, независимо от группы и категории.
- Может заполнить описание через AI; в панели свойств кнопка находится рядом с полем описания.

### Генерация `Описание` через AI

- Для авторских legacy-блоков в строке `KOTМетаданные -> Описание:` также доступна кнопка `Описать с помощью ИИ`.
- То же действие доступно командой `KOT - Generate KOT metadata description with AI`.
- Подробности по настройке, формату результата и поведению генерации вынесены в отдельный блок: [`ai-description.md`](./ai-description.md)

### Совместимость со штатным YAML СППР

Компилятор `BuildScenarioBDD` не читает `KOTМетаданные`. Этот блок нужен расширению; параметры, теги и шаги процессов используют штатные поля СППР.

Полностью заменить метаданные существующими полями СППР с сохранением поведения нельзя:

| Данные KOT | Возможность штатного формата |
|---|---|
| Группа Test Manager (`PhaseSwitcher.Tab`) | `УровеньОтчета1` и `УровеньОтчета2` могут стать основой группировки, но компилятор использует их для `report.feature` и `report.story`. Такое сопоставление потребует изменений KOT. |
| Порядок в группе (`OrderOnTab`) | Отдельного поля порядка библиотеки и Test Manager нет. Порядок шагов процесса задаёт порядок выполнения. |
| `Описание` | Загрузчик сценария не читает отдельное поле описания; извлечение из комментариев потребует соглашения KOT. |
| `Категория` библиотеки | Отдельного поля категории нет. `ТегиСценария` влияют на отбор и попадают в feature; соглашение о категориях через теги изменит эти данные. |

Служебные данные KOT сохраняются отдельно от штатных полей СППР, с привязкой к UID и совместимым чтением старых блоков. Новые правки описаний, категорий, групп и порядка следует выполнять через действия редактора или связанный соседний файл `*.kot.yml`.

## Кеш сценариев

### Что в кеше

- Имя, UID, код сценария.
- Информация о вложенных вызовах.
- Параметры сценария и дефолты.
- Метаданные для Test Manager.
- Сканирование идет по текущему корню сценариев; базовыми descriptor-файлами считаются `scen.yaml`.

### Как кеш обновляется

- Полный refresh при необходимости.
- Инкрементальные обновления после изменений сценариев.
- Пометка stale для run-артефактов при изменениях в связанных файлах.
- Сохранения неактивных сценариев попадают в очередь; их можно безопасно обработать пакетной командой `Repair changed scenarios`.

## Зависимости и влияние изменений

- Изменение вложенного сценария может влиять на главные сценарии выше по цепочке вызовов.
- Test Manager подсвечивает затронутые главные сценарии (если включено в настройках).
- Run-статус может переходить в `stale`, чтобы не вводить в заблуждение старыми «зелеными» результатами.

## Настройки блока

| Настройка | Назначение |
|---|---|
| `kotTestToolkit.phaseSwitcher.highlightAffectedMainScenarios` | Подсветка затронутых главных сценариев |
| `kotTestToolkit.editor.checkRelatedParentScenarios` | Проверка ошибок связанных родительских сценариев |
| Внутренний корень сканирования сценариев (синхронизируется из `ScenarioFolder`) | Область сканирования сценариев |

## Практические советы

- Держите текущий корень сценариев максимально точным (лишние папки = лишняя нагрузка).
- Для больших проектов используйте глобальный scan только при крайней необходимости.
- После крупных массовых правок делайте сборку заново, чтобы сбросить stale-статусы.
- После массовых правок (Replace in Files) используйте `Repair changed scenarios` для безопасной проверки и исправления структуры сценариев.
- Если нужно принудительно прогнать весь каталог сценариев, используйте `Repair all scenarios`, но это high-load операция.
