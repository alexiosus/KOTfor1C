# Блок: Создание сценариев

## Задача блока

Создавать новые главные и вложенные сценарии с согласованной шапкой YAML для `СборкаТекстовСценариев`, Test Manager и служебных функций расширения.

## Что входит в блок

### Команды

- `KOT - Создать вложенный сценарий`
- `KOT - Создать главный сценарий`
- `KOT - Создать процесс`
- `KOT - Нумерация тестов`
- `KOT - Управление функциями системы`
- `KOT - Управление эталонными базами`

### Что создает расширение

- Для вложенного сценария:
  - папку `<Код>/`;
  - файл `scen.yaml`;
  - папку `files/`.
- Для главного сценария:
  - папку `<Код>/`;
  - файл `scen.yaml` на основе шаблона `main.yaml`;
  - файл `test/<Код>.yaml` на основе шаблона `test.yaml`;
  - папку `files/`.

### Поток создания

1. Расширение запрашивает обычные пользовательские данные:
   - для вложенного сценария: `Имя`, родительскую папку, `Код`;
   - для главного сценария: `Имя`, родительскую папку, `Код`, группу Test Manager и порядок внутри неё.
   - Перед кодом каждый раз показывается выбор автора и серии; текущая серия стоит первой. Код предлагается из выбранной серии или вводится вручную; имя и код независимы.
2. Затем выбирается `ФункцияСистемы`:
   - если в каталоге настроена одна функция, она берется автоматически;
   - если функций несколько, показывается `QuickPick`.
3. Выбирается `Ответственный` из общего каталога `.kot/property-catalogs.yml`: можно создать имя или оставить поле пустым. Если код относится к авторской серии, её автор предлагается первым. Затем расширение спрашивает, как заполнить остальные служебные поля:
   - взять значения из `kotTestToolkit.newScenarioDefaults`;
   - или пройти по каждому полю вручную, но с предзаполнением значениями по умолчанию.
4. Для ручного режима по очереди запрашиваются:
   - `Проект` из общего каталога, с возможностью создать значение;
   - `РазрешеноИспользоватьВДругихФункциях`;
   - `ПрофильПользователя`;
   - `УровеньОтчета1` из общего каталога;
   - `УровеньОтчета2` из общего каталога.
5. Для главного сценария дополнительно выбираются данные `test.yaml`:
   - эталонная база из текущего `ModelDBSettings` (`bases.yaml`);
   - профиль пользователя из выбранной эталонной базы.
6. Если `bases.yaml` еще не заполнен, KOT не блокирует создание сценария:
   - можно создать тест и заполнить `ЭталоннаяБазаИмя`, `ИдентификаторБазы`, `ПрофильПользователя` позже;
   - для этого в `test.yaml` есть отдельные действия по карандашу.
7. После записи файлов расширение открывает созданный сценарий и обновляет Test Manager.

Мастер процессов также предлагает код, ответственного и короткий/полный режим заполнения своей шапки. В полном режиме доступны проект и уровни отчёта. База и профиль пользователя выбираются из каталога эталонных баз; поля, относящиеся только к сценариям, процессу не навязываются.

## Авторские серии и автонумерация

Серию можно настроить без палитры: откройте обычные настройки VS Code → **Каталоги проекта и нумерация**. Во вкладке **Workspace** или нужной **Folder** добавьте в **Numbering: Series** пару «шестизначный префикс → имя тестировщика». Во вкладке **User** задайте **Numbering: Prefix**, например `000012`. Серия должна существовать в общем каталоге проекта; для ручного ввода укажите `manual`. Личный префикс не переключает серию у коллег.

При каждом создании теста выберите существующую серию, добавьте свою или оставьте ручной ввод. **Numbering: Prefix** либо прошлый локальный выбор определяет первую строку списка. Серию можно сменить непосредственно в мастере; автор серии определяет нумерацию, а поле **Ответственный** задаётся отдельно. Предпочитаемую серию также можно изменить командой **KOT - Нумерация тестов**. Если префикс явно задан в настройках, команда обновит его в той же области настроек.

Первый вопрос мастера открывается до сканирования каталога. После ввода имени KOT проверяет существующие имена и коды; результаты этой проверки повторно используются для предложения номера. Перед созданием код ещё раз проверяется под блокировкой проекта.

Для добавления серии введите шестизначный префикс с ведущими нулями и выберите автора из каталога ответственных либо создайте имя. Например, серия `000012` предлагает `000012001`, затем `000012002`. Если в проекте уже есть `000012087`, следующий номер будет `000012088`. Код в мастере можно изменить; внутри настроенной серии нельзя повторно использовать уже выданный номер или старый пропуск.

Серии и последнее выданное значение хранятся в `.kot/test-numbering.yml`:

```yaml
version: 1
series:
  - prefix: "000012"
    author: "Имя тестировщика"
    lastNumber: 87
```

Префикс обязательно хранить строкой. Добавьте этот файл и `.kot/property-catalogs.yml` в Git. Новые реальные серии по примерам из документации автоматически не создаются. При первичной настройке KOT учитывает существующие коды; после удаления последнего теста сохранённый `lastNumber` не позволяет использовать его номер повторно. Серия заканчивается на `999`; соседняя серия автоматически не занимается.

У главных/вложенных сценариев и процессов общее пространство кодов. Настройки `test/<Код>.yaml` не расходуют отдельный номер серии: связь с определением задаёт UID. Смена имени, ответственного или группы не меняет код. Существующие файлы не перенумеровываются.

Автор серии определяет принадлежность выдаваемого номера тестировщику. `Ответственный` — отдельное поле СППР: при создании оно может совпадать с автором, но затем обозначать другого человека, сопровождающего тест. Поэтому KOT предлагает автора серии как начальное значение ответственного, позволяет заменить его и не выводит авторство существующих серий из этого поля.

Отмена мастера до создания не расходует предложенный номер. Если запись началась и завершилась ошибкой, номер остаётся выданным: пропуск безопаснее повторного использования. Операции выдачи и записи исходника защищены общей блокировкой проекта. Открытый изменённый каталог необходимо сохранить; чужие изменения и конфликтные YAML не перезаписываются. Временные `.kot/test-numbering.lock` и `.kot/test-numbering.yml.*.tmp` не нужно коммитить. Если после аварийного завершения остался lock, сначала убедитесь, что ни одно окно KOT не создаёт тест, затем удалите этот временный файл.

## Проверка кодов в CI

Независимые ветки одного автора всё ещё могут получить одинаковый номер. Перед слиянием запустите проверку из репозитория расширения, указав корень проекта и его авторские каталоги YAML:

```sh
npm run check:test-codes -- --project-root /path/to/project /path/to/project/tests/Yaml
```

Проверка читает сценарии и процессы, проверяет повторяющиеся коды и каталог серий, сохраняет ведущие нули. Настройки тестов и соседние KOT-метаданные не считаются отдельными тестами. Код возврата `1` означает ошибки. Проверка не меняет файлы; передавайте только нужные корни исходников, не общий корпус тестовых примеров. В существующий CI другого проекта команда автоматически не добавляется.

## Каталог `ФункцияСистемы`

### Как устроен

- Каталог хранится в `.kot/property-catalogs.yml` проекта, в разделе `systemFunctions`. Добавьте файл в Git, чтобы список был доступен другим тестировщикам.
- Если раздела ещё нет, KOT однократно переносит в него записи из старой настройки `kotTestToolkit.newScenarioDefaults.systemFunctions`. Существующие UID сохраняются. После переноса общий файл имеет приоритет над локальными настройками.
- Каждая запись содержит пару:
  - `name` — значение `ДанныеСценария.ФункцияСистемы`;
  - `uid` — значение `ДанныеСценария.UIDФункцияСистемы`.
- Первая запись в списке считается значением по умолчанию.

### Как редактируется

- В обычных настройках VS Code → **Каталоги проекта и нумерация** → **Catalogs: System Functions**, на вкладке **Workspace** или нужной **Folder**. Ключ таблицы — имя, значение — UID; пустой UID новой записи заполняется автоматически. Все общие каталоги доступны в этом же разделе: [подробности](shared-project-library.md#редактирование-в-обычных-настройках-vs-code).
- Через команду `KOT - Управление функциями системы`.
- Менеджер использует проект открытого исходника. Если исходника нет и проектов несколько, предлагает выбрать проект, включая внешние каталоги тестов.
- Новую запись также можно создать прямо из выпадающего списка функции системы в панели свойств. Все интерфейсы используют общий файл.
- В менеджере можно:
  - просмотреть текущий список;
  - добавить новую запись;
  - изменить имя;
  - изменить UID;
  - удалить запись;
  - сделать запись значением по умолчанию.

### Важное поведение

- Для новой функции системы UID генерируется автоматически.
- В YAML всегда записывается согласованная пара `ФункцияСистемы` + `UIDФункцияСистемы`.
- Это нужно, потому что `СборкаТекстовСценариев` использует `UIDФункцияСистемы` и `РазрешеноИспользоватьВДругихФункциях` для ограничения вызовов сценариев между функциями системы.

## Поля шапки сценария

Ниже перечислены основные поля, которые расширение подставляет при создании сценария.

| Поле | Для чего нужно | Кем используется |
|---|---|---|
| `ТипФайла` | Отличает сценарий от файла настройки запуска | `СборкаТекстовСценариев`, расширение |
| `ДанныеСценария.UID` | Основной идентификатор сценария | `СборкаТекстовСценариев`, Test Manager |
| `ДанныеСценария.Имя` | Человекочитаемое имя сценария | `СборкаТекстовСценариев`, расширение |
| `ДанныеСценария.Код` | Код сценария для тегов, JSON и диагностики | `СборкаТекстовСценариев`, расширение |
| `ДанныеСценария.Проект` | Проектный контекст сценария | в первую очередь `СборкаТекстовСценариев` |
| `ДанныеСценария.ФункцияСистемы` | Имя функции системы, к которой относится сценарий | `СборкаТекстовСценариев`, расширение |
| `ДанныеСценария.UIDФункцияСистемы` | GUID той же функции системы | `СборкаТекстовСценариев` |
| `ДанныеСценария.РазрешеноИспользоватьВДругихФункциях` | Разрешает или запрещает вызов из другой функции системы | `СборкаТекстовСценариев` |
| `ДанныеСценария.ПрофильПользователя` | Профиль TestClient по умолчанию | `СборкаТекстовСценариев`, запуск тестов |
| `ДанныеСценария.УровеньОтчета1` | Источник `#report.feature` в итоговом `feature` | `СборкаТекстовСценариев` |
| `ДанныеСценария.УровеньОтчета2` | Источник `#report.story` в итоговом `feature` | `СборкаТекстовСценариев` |
| `ПараметрыСценария` | Объявление параметров сценария | `СборкаТекстовСценариев`, расширение |
| `ВложенныеСценарии` | Связи с вызываемыми сценариями | `СборкаТекстовСценариев`, расширение |
| `ТекстСценария` | Основной текст Gherkin-сценария | `СборкаТекстовСценариев`, расширение |

### Что важно помнить

- Поля `ДанныеСценария.*` в основном нужны для совместимости с `СборкаТекстовСценариев`.
- Группы, порядок, категория и описание KOT хранятся в соседнем `*.kot.yml`; штатные шаблоны не вставляют `KOTМетаданные`. Авторские legacy-блоки сохраняются для совместимости, но не участвуют в BDD-сборке.
- Для большинства проектов разумно держать служебные значения в defaults и редко менять их вручную.

## Что записывается в `test.yaml`

`test.yaml` создается только для главного сценария и хранит настройки запуска теста.

| Поле | Назначение |
|---|---|
| `ТипФайла: "НастройкаТеста"` | Помечает файл как тестовую настройку |
| `ДанныеТеста.UID` | Отдельный UID самой настройки запуска |
| `ДанныеТеста.UIDСценария` | Ссылка на `ДанныеСценария.UID` главного сценария |
| `ДанныеТеста.Имя`, `Код`, `СценарийНаименование` | Отображаемое имя и код теста |
| `ДанныеТеста.ПрофильПользователя` | Профиль запуска; обычно выбирается из профилей текущей эталонной базы |
| `ДанныеТеста.ЭталоннаяБазаИмя` | Отображаемое имя эталонной базы из `bases.yaml` |
| `ДанныеТеста.ИдентификаторБазы` | Каноничный идентификатор эталонной базы из `bases.yaml`; по нему СППР ищет `DT`, логин и пароль |
| `ДанныеТеста.ПараметрыЗапуска`, `ПараметрыТеста` | Дополнительные параметры запуска и настройки запуска |

## Редактирование `test.yaml`

В редакторе `test/*.yaml` доступны действия по карандашу:

- для `ЭталоннаяБазаИмя` / `ИдентификаторБазы`:
  - открыть picker эталонных баз;
  - синхронно обновить оба поля;
- для `ПрофильПользователя`:
  - выбрать профиль из текущей эталонной базы;
- для `Код`, `UIDСценария`, `Имя`, `СценарийНаименование`:
  - открыть меню `Change linked scenario`;
  - переименовать связанный сценарий;
  - синхронизировать поля из соседнего `scen.yaml`;
  - перелинковать `test.yaml` на другой главный сценарий.

## Быстрый переход из `scen.yaml`

- В шапке главного `scen.yaml` доступно быстрое действие `Open run settings`.
- Оно открывает связанный `test.yaml`, не требуя искать его через дерево проекта или контекстное меню Test Manager.
- Подробнее о каталоге эталонных баз: [etalon-bases.md](./etalon-bases.md)

## Практические советы

- Если проект использует один и тот же набор служебных значений, держите их в `newScenarioDefaults` и не дублируйте вручную в каждом YAML.
- Каталог функций системы редактируется в **Catalogs: System Functions** настроек VS Code или в менеджере функций. Значение поля конкретного теста выбирается в его свойствах.
- Если хотите, чтобы новые `test.yaml` сразу создавались с корректной эталонной базой и профилем, сначала заполните `ModelDBSettings` / `bases.yaml`.
- Изменение имени главного сценария сохраняет код и пути. Папка сценария и основной файл в `test/` следуют изменению кода.
- Наведением на ключи шапки в YAML можно посмотреть краткое описание поля прямо в редакторе, в том числе для `test.yaml`.
